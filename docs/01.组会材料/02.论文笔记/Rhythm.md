# Rhythm: Learning Interactive Whole-Body Control for Dual Humanoids

- Project Link: [https://hoshi-no-ai.github.io/Rhythm/](https://hoshi-no-ai.github.io/Rhythm/)
- Paper Link: [https://arxiv.org/pdf/2603.02856](https://arxiv.org/pdf/2603.02856)

## 模型框架图

这篇 **Rhythm** 主要解决的是一个比较新的问题，就是**双 humanoid 之间的交互式全身控制**。以往的人形机器人控制工作大部分还是针对单机器人，比如让一个机器人行走、跑步、操作物体或者跟踪人体动作。但是当两个机器人发生真正的身体接触以后，比如握手、拥抱或者一起跳舞，两个机器人的运动就不再是相互独立的，一个机器人的动作会直接改变另一个机器人的受力和运动状态，因此本质上变成了一个**双机器人耦合动力学控制问题**。Rhythm 整体上提出了三个部分，分别是左边的 **IAMR，也就是 Interaction-Aware Motion Retargeting**，中间的 **IGRL，也就是 Interaction-Guided Reinforcement Learning**，以及右边的真实机器人 Deployment。论文最终在两台 Unitree G1 上验证了这套方法。

左边的输入是一个 **Human-Human Interaction Dataset**，也就是人和人之间的交互动作数据。这里的核心问题是，不能简单地把两个人的动作分别 Retarget 到两个机器人上。因为人体和 humanoid 的身体比例不同，如果分别进行 Retarget，可能出现一种情况，就是每个机器人自己的动作看起来都没有问题，但是两个机器人之间的交互关系已经被破坏了。比如原来两个人是在握手，映射到两个 G1 以后可能出现两个手够不到，或者两个人的手臂、身体发生穿模。因此，Rhythm 在这里并不是单纯考虑“机器人自己怎么运动”，而是同时考虑“两个机器人之间怎么交互”。论文将这个问题归纳为双机器人之间严重的运动学不匹配问题。

具体来看图中左边的人体骨架，这里面黑色的边叫做 **Intra-Agent Edges，也就是 EselfE_{self}**，表示一个机器人自身身体内部的连接关系，例如肩膀到肘部、肘部到手，或者髋关节到膝关节、膝关节到脚。这部分主要保证**单个机器人的动作质量和运动学合理性**。而图中的红色边叫做 **Inter-Agent Edges，也就是 EinterE_{inter}**，它连接的是两个不同机器人之间的关键点，例如机器人 A 的手和机器人 B 的肩膀、手或者身体之间的关系。这部分描述的是**两个机器人之间的交互几何关系**。所以作者实际上把原来一个比较复杂的双人 Retargeting 问题拆成了两类约束：一类保证机器人自己动作正确，另一类保证机器人之间的相对关系正确

然后图中间这个 **Decoupled Optimization** 就是在解决这两个目标之间的冲突。因为如果只追求 Self-Motion Fidelity，也就是尽可能保持机器人的自身动作，那么两个机器人之间可能发生接触错位甚至穿模；如果只追求 Interaction Geometry，又可能为了维持两个人之间的距离而牺牲机器人自身的运动可行性。所以作者将这两个目标进行解耦优化，在保证机器人自身运动质量的同时，再尽可能保持两个机器人之间的交互几何关系。最终左下角得到三类 **Motion References**：首先是机器人本身的 **Trajectory**，也就是后面控制器要跟踪的运动轨迹；其次是 **Interaction Graph**，描述两个机器人关键部位之间的空间关系；最后是 **Contact Graph**，描述交互过程中哪些身体部位应该发生接触。也就是说，IAMR 的最终目的并不是简单产生一条机器人轨迹，而是生成一套**同时包含运动、交互拓扑和接触关系的双机器人参考数据**。

有了左边 IAMR 生成的参考动作以后，还不能直接把这些轨迹发送给真实机器人，因为双机器人发生接触以后存在非常复杂的动力学。例如一个机器人向前走了一步，它的身体可能推动另一个机器人；另一个机器人为了保持平衡又必须调整自己的腿和躯干。因此作者进一步提出 **IGRL，也就是 Interaction-Guided Reinforcement Learning**，让两个机器人通过强化学习真正学会这种**相互影响的耦合动力学**。论文采用的是多智能体强化学习框架，并使用 MAPPO，在训练过程中让两个机器人共同学习，而部署时再进行分布式执行。

从图中上面的 Policy Network 可以看到，每个机器人并不是只看自己的状态。它的输入主要可以理解成三部分：第一部分是 **opropo_{prop}，也就是 proprioception，本体状态**，包括机器人自身的关节状态、速度等信息；第二部分是 **opeero_{peer}，也就是 peer observation，用来描述另外一个机器人相对于自己的状态**；第三部分是 **orefo_{ref}，也就是 reference motion，提供当前以及未来一段时间的参考动作信息**。所以这里和传统单机器人 Motion Tracking 最大的区别就是，机器人不仅知道“我现在应该怎么动”，还知道“对面的机器人在哪里，以及接下来要怎么动”。这样策略才有可能提前调整自己的动作来配合对方。

然后这些信息经过图中的 **State Encoder 和 Command Encoder** 编码以后进入 Policy Network，再通过 **Action Decoder** 输出动作。图中下面的两个机器人分别对应策略 πA\pi_A 和 πB\pi_B。这里需要特别注意，作者不是训练两个完全互不相关的单机器人策略，而是让两个 agent 在训练过程中共同考虑彼此的状态和交互关系。因此，整个控制过程实际上是：

**机器人 A 感知自己和机器人 B → 策略计算动作 → A 运动以后改变 B 的状态 → B 根据新的状态调整动作 → 两个机器人不断相互影响。**

所以作者把左边 IAMR 得到的 **Interaction Graph 和 Contact Graph** 继续传递到强化学习阶段，并构造了图结构奖励。图中首先有一个 **Interaction Graph Reward rinterr_{inter}**，它主要约束两个机器人之间的几何关系。比如参考动作要求 A 的手和 B 的肩膀保持一定的相对距离，那么强化学习过程中就会持续检查当前两个关键点之间的关系是否符合参考交互结构。这样机器人不会只关注自己的关节轨迹，还必须关注自己和另一个机器人之间的空间关系。

另外还有一个 **Contact Graph Reward rcontactr_{contact}**，它进一步关注实际接触。也就是说，在参考动作要求发生接触的时候，两个机器人需要真正形成正确的接触；而在不应该接触的位置，则需要避免错误碰撞。因此整个 RL 的优化目标可以理解成三层：第一层是**机器人自身动作跟踪**，第二层是**两个机器人之间的交互几何保持**，第三层是**实际接触关系保持**。这样才能让策略真正学到“和另一个机器人一起运动”，而不是两个机器人各自模仿自己的轨迹。论文明确将 IGRL 描述为通过 graph-based rewards 学习双机器人耦合动力学。

这里最关键的是状态估计和两个机器人之间的同步。图的最上面是 **State Estimation**，机器人通过 LiDAR 点云进行环境感知，然后经过 **Localization** 得到自己的 Global Pose。由于两个机器人是在真实环境中运动的，所以控制器不能简单使用仿真中的理想全局状态，而需要实时估计两个机器人的真实位置。得到两个机器人的 Global Pose 以后，系统进一步计算 **Relative Pose**，也就是“机器人 A 相对于机器人 B 在哪里”。例如 A 在 B 的左前方多远、朝向是什么。这个相对位姿信息就会进一步提供给前面 IGRL 的 peer observation，使机器人能够知道对方当前在哪里。另外，图中还有一个 **Inter-Agent Synchronization**，也就是机器人之间的同步。两个机器人通过图中的 **Wireless LCM** 交换信息，使两个策略能够保持一致的运动节奏。因为对于拥抱、跳舞这类任务，仅仅知道对方在哪里还不够，还必须知道对方现在处于动作的哪个阶段。如果 A 已经开始伸手，而 B 还没有准备好，就很容易出现交互失败。因此作者还设计了双机器人之间的同步机制，最终让两个机器人能够保持协调的运动相位。
