## Linux 基础认知

不同的操作系统通常会基于不同设计思路，面向不同的用户群体，因此从用户的使用感受来说往往大相径庭。然而由于现代个人计算机操作系统的功能高度相似，因此它们在不同的外表下存在着诸多共通的属性。只要进行一些调研，我们就能发现它们实际上殊途同归。

### 什么是 Linux

Linux 是一个开源的类 Unix 操作系统内核，最初由芬兰程序员 Linus Torvalds 于 1991 年发布。严格来说，Linux仅指内核（kernel），负责管理 CPU、内存、磁盘、网络等硬件资源，并为上层程序提供系统调用接口。我们日常所说的Linux 系统，通常是指以 Linux 内核为核心、配合 GNU 工具链、系统库、包管理器和应用软件组成的完整操作系统，因此更准确的称呼是 GNU/Linux。

Linux 采用 GPL 等开源许可证发布，任何人都可以自由使用、修改和分发其源代码，这一开放性使其从个人爱好项目成长为支撑互联网、云计算、超级计算和嵌入式设备的主流平台，Linux 内核本身不提供图形界面，图形环境、命令行工具和各类服务都由发行版在其上构建。


### Linux 与 Unix 的关系

Unix 诞生于 1969 年，由 AT&T 贝尔实验室的 Ken Thompson、Dennis Ritchie 等人开发，是早期最具影响力的多用户、多任务操作系统。Unix 的设计哲学为**一切皆文件、小工具组合、管道与文本流**，这也深刻影响了后续操作系统。

Linux 并非 Unix 的衍生代码，而是从零编写的类 Unix 系统。它遵循 POSIX 标准，在系统调用、命令行工具和编程接口上与 Unix 保持高度兼容，因此大量 Unix 程序可以较容易地移植到 Linux 上。二者关系可以概括为：Unix 是设计理念与标准的源头，Linux 是独立实现且兼容这些理念的开源系统。由于商标原因，Linux 一般被称为类 Unix（Unix-like）系统，而非Unix。


### Linux 发行版简介

一个典型的 Linux 发行版除了 Linux 内核以外，通常还会包括一系列 GNU 工具和库、一些附带的软件、说明文档、一个桌面系统、一个窗口管理器和一个桌面环境。不同的发行版之间除了 Linux 内核以外的其它部分都有可能不一样，因此有的时候我们对比某两种发行版的时候会觉得它们看起来像是完全不一样的操作系统，然而实质上它们却拥有着相同的核心，即 Linux 内核。

### Linux 的特点与应用场景

Linux 的主要特点包括：

- 开源自由：源代码公开，可自由修改与分发，社区和企业共同维护；
- 多用户、多任务：支持多用户同时登录、多任务并行运行，权限体系清晰；
- 稳定可靠：内核设计成熟，服务器可长期运行而无需频繁重启；
- 可移植性强：支持 x86、ARM、RISC-V、MIPS 等多种硬件架构；
- 网络功能强大：TCP/IP 协议栈完善，是服务器与网络设备的主流平台；
- 安全性好：权限模型、命名空间、SELinux/AppArmor 等机制提供多层隔离与访问控制；
- 高度可定制：从内核裁剪到桌面环境均可按需配置，适应从嵌入式到超算的不同规模。

其典型应用场景包括：
- Web 与数据库服务器、云计算与容器平台（Docker、Kubernetes 大多运行在 Linux 上）、
- 超级计算机（TOP500 中绝大多数运行 Linux）、
- 嵌入式与物联网设备（路由器、智能家居、车载系统）、
- Android 系统（基于 Linux 内核），以及开发者的桌面与编程环境。

## Linux 系统架构

![Linux 系统架构](https://ubuntu-picupload-1330431167.cos.ap-guangzhou.myqcloud.com/images/20261105225027910.png)

### Linux 整体架构

Linux 系统采用分层结构，自上而下大致可分为四层：最上层是**用户应用程序**，中间是 **Shell 与系统库（如 glibc）**，再往下是**内核（Kernel）**，最底层是**硬件**。应用程序一般不直接操作硬件，而是通过系统库或 Shell 提供的接口，经由**系统调用**请求内核服务，由内核统一调度 CPU、内存、磁盘、网卡等硬件资源。

这一分层在逻辑上体现为两个空间的划分：内核运行在**内核空间**，拥有对硬件的完全控制权；应用程序、Shell 和系统库运行在**用户空间**，权限受限，只能通过系统调用进入内核。Shell 本身也是用户空间的一个普通程序，它与系统库处于同一层，负责解析用户输入的命令并启动相应程序，并不属于内核的一部分。

从功能组成看，一个完整的 Linux 系统通常包括：内核（进程管理、内存管理、文件系统、网络协议栈、设备驱动）、系统库（C 库及各类运行时）、Shell 与命令行工具（GNU coreutils 等）、图形环境（X11/Wayland 与桌面环境）、包管理器，以及各类应用服务。其中内核是唯一直接与硬件打交道的部分，其余组件都构建在内核提供的抽象之上。

### 内核（Kernel）

内核是操作系统的核心，是运行在内核空间、直接管理硬件资源的程序。它向上为应用程序提供统一的抽象接口，向下屏蔽不同硬件的差异，主要承担五类职责：**进程调度**（决定哪个进程何时使用 CPU）、**内存管理**（虚拟内存、分页、地址空间隔离、页缓存）、**虚拟文件系统**（VFS 统一抽象 ext4、XFS、Btrfs、NFS 等具体文件系统）、**网络协议栈**（TCP/IP、套接字接口、网络设备驱动）、**进程间通信**（管道、信号、共享内存、消息队列、socket）。设备驱动也属于内核的一部分，负责与具体硬件交互。

按体系结构分类，Linux 属于**宏内核**（monolithic kernel），即进程调度、内存管理、文件系统、网络等核心功能都运行在同一内核地址空间中，模块间通过函数调用直接通信，性能较高；与之相对的微内核则把这些功能拆成独立服务进程，通过消息传递通信。为兼顾宏内核的性能与灵活性，Linux 支持**可加载内核模块**（Loadable Kernel Module，LKM），驱动和部分功能可以在运行时用 `insmod`/`modprobe` 动态加载或卸载，无需重新编译和重启内核。

内核版本号通常形如 `6.8.0-45-generic`，由主版本号、次版本号、修订号及发行版后缀组成。历史上次版本号为偶数表示稳定版、奇数为开发版，但这一规则在 3.x 之后已不再严格遵循。内核通过 `/proc` 和 `/sys` 两个伪文件系统向用户空间暴露运行时信息与可调参数，例如 `/proc/cpuinfo`、`/proc/meminfo`、`/sys/class/net/` 等，用户可借助 `sysctl` 或直接读写这些文件查看和调整内核行为。

### Shell

Shell 是运行在用户空间的**命令解释器**，是用户与操作系统交互的接口。它读取用户输入的命令行，解析其中的命令名、参数、管道和重定向，找到对应的可执行文件并启动它，等待其结束后再读取下一条命令。Shell 本身是一个普通用户态程序，不是内核组件，它完成的所有实际工作（如打开文件、创建进程）最终都要通过系统调用请求内核。

常见的 Shell 包括：**bash**（Bourne Again Shell，GNU 项目开发，多数 Linux 发行版的默认 Shell）、**sh**（POSIX 标准 Shell，在 Debian/Ubuntu 上通常由 dash 实现）、**zsh**（功能丰富、可定制性强，macOS 默认）、**fish**（语法友好、自动补全强）、**ksh**（Korn Shell）、**csh/tcsh**（C Shell，语法接近 C 语言）。不同 Shell 在语法细节、变量处理、补全与提示符配置上存在差异，但都遵循 POSIX 的基本命令语法。

Shell 的核心工作机制可以概括为“读取—解析—执行—等待”循环：读取一行命令后，先做变量替换、通配符展开、引号处理等解析工作，再判断是内建命令（如 `cd`、`echo`、`export`，由 Shell 自身执行）还是外部命令；对外部命令，Shell 通过 `fork` 创建子进程，在子进程中用 `execve` 加载并执行目标程序，父进程用 `wait` 等待其结束并取得退出状态。管道 `|`、重定向 `>`、`<`、后台运行 `&` 等机制也由 Shell 在这一过程中通过系统调用建立。

除交互式使用外，Shell 还支持脚本编程，把一系列命令写入文件并按顺序执行，配合条件判断、循环、函数和变量，可完成自动化运维任务。用户的默认 Shell 记录在 `/etc/passwd` 对应条目的最后一个字段中，系统可用的合法 Shell 列表通常登记在 `/etc/shells` 中，用户可用 `chsh` 命令修改自己的登录 Shell。

### 系统调用（System Call）

系统调用是**用户空间程序请求内核提供服务的唯一合法入口**，是用户态与内核态之间的受控通道。当程序需要读写文件、申请内存、创建进程、发送网络数据等操作时，必须通过系统调用陷入内核，由内核在特权级下完成实际工作，再把结果返回用户空间。这一机制保证了用户程序无法绕过内核直接操作硬件或访问其他进程的数据。

系统调用与库函数不同：库函数（如 `printf`、`malloc`）是用户空间中的普通函数，由 C 库实现，可能完全不涉及内核（如纯计算的 `strlen`），也可能在内部封装系统调用（如 `printf` 最终调用 `write`，`malloc` 在需要扩展堆时调用 `brk` 或 `mmap`）。程序员通常通过库函数间接使用系统调用，但系统调用本身才是内核暴露的原始接口。

常见的系统调用按功能可分为几类：**进程控制**（`fork`、`vfork`、`clone`、`execve`、`exit`、`wait4`）、**文件操作**（`open`、`read`、`write`、`close`、`lseek`、`stat`、`dup`、`pipe`）、**内存管理**（`brk`、`mmap`、`munmap`、`mprotect`）、**网络通信**（`socket`、`bind`、`listen`、`accept`、`connect`、`sendto`、`recvfrom`）、**信号**（`kill`、`sigaction`、`sigprocmask`）、**进程间通信**（`shmget`、`msgget`、`semop`）以及**时间与系统信息**（`clock_gettime`、`getpid`、`uname`）等。

在实现上，用户程序执行一条特定的陷入指令（x86-64 上为 `syscall`，32 位 x86 上为 `int 0x80` 或 `sysenter`，ARM 上为 `svc`），把系统调用号放入约定寄存器，CPU 从用户态切换到内核态，内核根据系统调用号在系统调用表中找到对应处理函数并执行，参数通过寄存器传递，返回值同样经寄存器带回。Linux 的系统调用接口遵循 POSIX 标准，因此同一套程序在不同类 Unix 系统上通常只需少量修改即可编译运行。实际调试中，可用 `strace` 工具跟踪一个程序发起了哪些系统调用及其参数与返回值，这是排查程序行为的重要手段。

### 用户空间与内核空间

现代操作系统把虚拟地址空间划分为**用户空间**和**内核空间**两部分，这一划分既体现在地址范围上，也体现在 CPU 特权级上。以 64 位 x86 为例，进程的虚拟地址空间被分为低地址的用户空间与高地址的内核空间，用户程序只能访问低地址部分，内核代码和数据位于高地址部分。相应地，CPU 提供多个特权级（x86 上常用的 ring 0 与 ring 3）：内核运行在 ring 0，可执行特权指令、访问全部内存与硬件端口；用户程序运行在 ring 3，特权指令被禁止，访问受限地址会触发异常。

这种隔离的目的在于**保护与稳定**。用户程序无法直接读写内核数据结构，也无法直接操作硬件寄存器或设备端口，从而避免一个程序的错误破坏整个系统。用户态进程崩溃（如段错误）只会终止该进程，内核和其他进程不受影响；反之，内核态出现严重错误则可能导致整个系统崩溃（panic）。同时，隔离也提供了安全边界：不同进程的用户空间彼此独立，一个进程无法随意读取另一个进程的内存，权限控制由此得以建立。

用户空间与内核空间之间的交互必须通过受控接口完成。主要方式包括：**系统调用**（最主要的通道）、**伪文件系统** `/proc` 与 `/sys`（以文件读写形式暴露内核信息与参数）、**netlink 套接字**（用户态与内核网络子系统通信）、**设备文件**（通过 `/dev` 下的设备节点与驱动交互）以及**信号**等。由于两个空间地址映射不同，内核在系统调用中与用户空间交换数据时必须使用 `copy_from_user`、`copy_to_user` 等专用函数，而不能直接解引用用户指针。

这种划分也带来一定开销：每次系统调用都要经历特权级切换、保存与恢复上下文、可能冲刷部分缓存与 TLB 条目，因此频繁的小规模系统调用会显著影响性能。这解释了为什么许多程序采用缓冲 I/O（如标准库的 `FILE` 缓冲）、批量读写、`mmap` 映射文件或 `io_uring` 异步接口来减少陷入内核的次数。理解用户空间与内核空间的边界及其交互方式，是理解 Linux 性能特征与安全模型的基础。

##  Linux 文件系统基础

### 什么是文件系统

文件系统（File System）是操作系统用来组织和存储文件的一套规则与结构。磁盘等存储设备本身只是一块可以按字节读写的空间，文件系统负责在这块空间上建立目录、记录每个文件的名字、位置、大小、权限和创建时间等信息，并让用户能够按名称方便地存取数据，而不必关心数据实际落在磁盘的哪个扇区。

可以把文件系统理解为图书馆的索引系统：书（数据）存放在书架上，索引卡（元数据）记录每本书的位置和编号，读者只需按书名查找，就能拿到对应的书。文件系统做的正是类似的事——把零散的存储空间组织成有名字、有层级、可检索的文件和目录。

在 Linux 中，文件系统是**挂载（mount）**到目录树上的。一块硬盘分区、一个 U 盘、甚至一个网络共享，都可以被挂载到某个目录下，用户通过该目录访问其中的内容。Linux 支持多种文件系统类型，常见的有 ext4、XFS、Btrfs、FAT32、NTFS、NFS 等，它们各自的内部结构不同，但都通过统一的接口呈现给用户。

### Linux 文件系统的特点

与 Windows 相比，Linux 文件系统有几个显著特点，初学者需要特别留意：

**单一的树形结构，没有盘符。** Windows 用 C:、D: 等盘符区分不同分区，而 Linux 只有一个根目录 `/`，所有文件和目录都从 `/` 出发形成一棵树。不同的分区、硬盘、U 盘通过挂载点接入这棵树，例如系统盘挂在 `/`，另一块数据盘可以挂在 `/data`，用户感觉不到它们来自不同设备。

**一切从根开始，路径分隔符为斜杠 `/`。** Linux 使用 `/` 分隔路径层级（Windows 用反斜杠 `\`），根目录写作 `/`，例如 `/home/user/docs`。

**严格区分大小写。** `file.txt`、`File.txt`、`FILE.TXT` 是三个不同的文件。这一点与 Windows 不同，初学者在复制文件或写脚本时容易因此出错。

**文件名长度和字符限制较宽松。** 文件名最长通常可达 255 个字符，除 `/` 和空字符外几乎可以使用任何字符，但建议避免空格、`*`、`?`、`$` 等在 Shell 中有特殊含义的字符。

**文件类型由元数据标识，而非扩展名。** Linux 不靠 `.txt`、`.exe` 这类后缀判断文件类型，而是通过文件自身的属性（如是否可执行、文件头魔数）识别。扩展名更多是给人看的约定，例如 `.sh` 表示 Shell 脚本、`.conf` 表示配置文件。

**统一的目录规范（FHS）。** 主流发行版遵循文件系统层次标准，常见目录有明确分工：`/bin` 与 `/usr/bin` 存放可执行命令，`/etc` 存放系统配置，`/home` 存放普通用户的家目录，`/var` 存放经常变化的数据（如日志），`/tmp` 存放临时文件，`/dev` 存放设备文件，`/proc` 与 `/sys` 是内核暴露信息的伪文件系统，`/mnt` 与 `/media` 常作为挂载点。熟悉这些目录的作用，有助于快速定位系统中的文件。

### 一切皆文件

“一切皆文件”（Everything is a file）是 Unix/Linux 设计中最具代表性的哲学之一。它的含义是：系统中的许多资源都被抽象成文件的形式，用户可以用统一的 `open`、`read`、`write`、`close` 等操作来访问它们，而不必为每种资源学习一套专门的接口。

具体来说，以下资源在 Linux 中都表现为文件：

- **普通文件**：文本、二进制程序、图片等，最直观的文件；
- **目录**：本身也是一种文件，记录其中包含哪些文件名；
- **设备文件**：硬盘、键盘、串口等硬件设备在 `/dev` 下有对应的设备文件，向设备文件写入数据就等于向硬件发送数据；
- **管道**：进程间通信用的管道以文件形式存在，可用读写文件的方式读写管道；
- **套接字（socket）**：网络通信端点也以文件形式呈现；
- **伪文件系统**：`/proc`、`/sys` 中的文件并不真正存储在磁盘上，读写它们实际是在读取内核状态或修改内核参数，例如 `/proc/cpuinfo` 显示 CPU 信息，`/sys/class/leds/` 下的文件可用于控制 LED；
- **标准输入输出**：每个进程默认打开的 `stdin`、`stdout`、`stderr` 也是文件描述符，可以像文件一样重定向。

这种统一抽象的好处是显而易见的：同一条命令（如 `cat`、`echo`、重定向 `>`）既能处理普通文本，也能读取设备、查看内核信息、写入伪文件，大大降低了学习和使用的复杂度。理解“一切皆文件”，是理解 Linux 命令行操作方式的关键一步。

### 文件与目录的关系

在 Linux 中，**目录本身也是一种文件**，只不过它是一种特殊类型的文件，内容不是普通数据，而是“文件名到 inode 的映射表”。inode（索引节点）是文件系统中用来存储文件元数据的结构，记录了文件的类型、大小、权限、所有者、时间戳以及数据块的位置，而文件名只是指向 inode 的一个入口。

这就解释了几个初学者常困惑的现象：

**同一个文件可以有多个名字。** 多个文件名可以指向同一个 inode，这称为**硬链接**。删除其中一个名字并不会删除文件内容，只有当指向该 inode 的所有硬链接都被删除、且没有进程打开该文件时，数据才真正被释放。

**目录不能通过硬链接被随意连接。** 为避免目录树出现环，普通用户不能为目录创建硬链接（符号链接则可以）。

**移动文件可能只是改名字。** 在同一文件系统内用 `mv` 重命名或移动文件，往往只改变目录中的映射关系，数据块并未搬动，因此速度极快。

**目录的层级构成路径。** 根目录 `/` 是整棵树的起点，每个目录下可以包含子目录和文件，形成树形结构。目录中的 `.` 表示当前目录本身，`..` 表示上一级目录，这两个特殊条目在每个目录中都存在，方便在路径中引用。

**文件名与文件内容是分离的。** 重命名文件不会改变其内容，改变文件内容也不影响其名字；删除文件时，删除的是目录中的名字与 inode 的链接，而非 inode 本身立即消失（引用计数减到零才回收）。

理解“目录是特殊文件、文件名指向 inode”这一模型，有助于正确理解硬链接、软链接、删除、重命名等操作的实际行为。

### 文件类型

Linux 中用 `ls -l` 查看目录时，每行第一个字符表示文件类型，常见类型如下：

| 类型标识 | 名称 | 说明与示例 |
|---|---|---|
| `-` | 普通文件 | 文本、二进制、图片、压缩包等，如 `/etc/passwd`、`/bin/ls` |
| `d` | 目录 | 包含其他文件或子目录，如 `/home`、`/etc` |
| `l` | 符号链接（软链接） | 指向另一个路径的“快捷方式”，如 `/usr/bin/python3 -> python3.12` |
| `b` | 块设备文件 | 按块随机读写的设备，如硬盘 `/dev/sda`、分区 `/dev/sda1` |
| `c` | 字符设备文件 | 按字符流读写的设备，如终端 `/dev/tty0`、空设备 `/dev/null` |
| `p` | 命名管道（FIFO） | 用于进程间通信的管道文件，可用 `mkfifo` 创建 |
| `s` | 套接字（socket） | 用于进程间或网络通信，常见于 `/run` 下的服务套接字 |

![文件类型](https://ubuntu-picupload-1330431167.cos.ap-guangzhou.myqcloud.com/images/20261105225306400.png)

**普通文件**是最常见的类型，又可分为文本文件和二进制文件。文本文件由可读字符组成，如配置文件、脚本、日志；二进制文件由机器指令或特定格式数据组成，如可执行程序、图片、压缩包。Linux 不靠扩展名区分二者，但习惯上仍用 `.sh`、`.conf`、`.log`、`.png` 等后缀提示用途。

**符号链接**是一个独立文件，内容是指向目标的路径字符串。访问符号链接时，系统会自动跳转到目标；若目标被删除，符号链接就变成“悬空链接”，访问时会报错。符号链接可以指向目录，也可以跨文件系统，这与硬链接不同。用 `ln -s 目标 链接名` 创建。

**设备文件**位于 `/dev` 下，是内核设备驱动在用户空间的接口。块设备按固定大小的块访问，适合存储设备；字符设备按字节流访问，适合终端、串口、传感器等。初学者常用的 `/dev/null` 是字符设备，写入它的数据会被丢弃，常用来丢弃不需要的输出；`/dev/zero` 可产生无限个零字节。

**命名管道**用 `mkfifo` 创建，两个进程可以像读写普通文件一样通过它传递数据，数据不落地磁盘，读完即消失。

**套接字**用于本机进程间通信（Unix domain socket）或网络通信，数据库、Web 服务器等常用它在 `/run` 下创建通信端点。

识别文件类型除了看 `ls -l` 的首字符，还可以用 `file 文件名` 命令，它会根据文件内容（魔数）判断实际类型，比扩展名更可靠。

### 绝对路径与相对路径

**绝对路径**是从根目录 `/` 开始的完整路径，无论当前处于哪个目录，它都唯一指向同一个位置。例如 `/home/alice/docs/report.txt` 表示根目录下的 `home` 目录中的 `alice` 目录中的 `docs` 目录中的 `report.txt`。绝对路径总是以 `/` 开头，含义明确、不受当前位置影响，适合在脚本和配置文件中使用。

**相对路径**是从当前工作目录出发的路径，不以 `/` 开头。例如当前在 `/home/alice` 时，`docs/report.txt` 就表示 `/home/alice/docs/report.txt`。相对路径更简短，适合在命令行中快速操作，但它的含义依赖当前目录，换一个位置就可能指向别处。

路径中还有两个特殊符号：`.` 表示当前目录，`..` 表示上一级目录。例如 `./run.sh` 表示当前目录下的 `run.sh`，`../config` 表示上一级目录中的 `config`。`~` 表示当前用户的家目录，`~alice` 表示用户 alice 的家目录，它们会在 Shell 中被展开为绝对路径。

用 `pwd` 命令可以查看当前工作目录的绝对路径；用 `cd` 切换目录时，`cd /etc` 使用绝对路径，`cd ../var` 使用相对路径，`cd` 不带参数则回到当前用户的家目录。初学阶段建议在不确定位置时多用 `pwd` 确认，在脚本中优先使用绝对路径，以避免因当前目录变化导致意外错误。

绝对路径与相对路径并无优劣之分，关键在于场景：交互式操作时相对路径更便捷，需要稳定指向某文件时绝对路径更可靠。理解二者的区别与转换方式（如 `realpath` 命令可将相对路径解析为绝对路径），是熟练使用 Linux 命令行的重要基础。

## Linux 目录结构

### Linux 根目录

Linux 文件系统是一棵以 `/` 为唯一根节点的树。无论系统挂载了多少块硬盘、多少个分区，它们都通过“挂载”接入这棵树，而不是像 Windows 那样用 C:、D: 等盘符并列展示。根目录 `/` 就是这棵树的起点，所有其他目录和文件都位于它之下。

根目录本身承载的内容应当尽量“最小”。FHS 要求根文件系统只包含启动、恢复、修复和基本运行所必需的文件，不应存放应用程序特有的目录；所有附加软件和可变数据应放到 `/usr` 或 `/var` 中。这样做的好处是：根分区可以从最小的恢复介质挂载，减少数据损坏的影响，也便于在存储受限或独立分区时维护。

从内容上看，根目录下的子目录大致分为三类。第一类是**启动和基本运行所必需**的：`/bin`、`/sbin`、`/lib`、`/etc`、`/dev`，它们必须在根分区上物理存在，否则系统无法启动。第二类是**挂载点和运行状态**：`/media`、`/mnt` 用于挂载外部文件系统，`/run` 存放本次启动以来的运行时数据，`/proc` 和 `/sys` 是内核暴露信息的虚拟文件系统。第三类是**数据与服务入口**：`/home` 存放普通用户文件，`/root` 是管理员的家目录，`/srv` 存放系统对外提供的数据，`/opt` 用于附加软件包。

### 核心目录说明

**/bin** 存放所有用户（包括普通用户）在启动和日常操作中需要的基本命令，如 `ls`、`cp`、`mv`、`sh` 等。这些命令在单用户模式下也必须可用，因此 `/bin` 必须位于根分区上。

**/sbin** 与 `/bin` 类似，但存放的是系统管理和修复用的二进制程序，如 `fsck`、`shutdown`、`reboot` 等，通常面向 root 用户或需要特权才能执行的操作。简单记法是：`s` 代表 system 或 super，`/sbin` 下的命令用于系统级维护。

**/lib** 存放 `/bin` 和 `/sbin` 中程序运行所需的基本共享库和内核模块。这些库类似于 Windows 中的 DLL，是程序启动和运行不可或缺的依赖。

**/etc** 存放**特定于本机的系统配置文件**，几乎所有服务的配置都集中在这里，如 `/etc/passwd`、`/etc/fstab`、`/etc/hosts`。FHS 明确要求 `/etc` 不应包含二进制可执行文件；它存放的是纯文本配置，方便管理员查看和修改。

**/home** 是普通用户家目录的父目录，每个用户在 `/home` 下拥有以自己用户名命名的子目录，个人文件、配置和桌面环境设置都保存在这里。root 用户的家目录不在 `/home` 下，而是单独的 `/root`。

**/root** 是超级用户 root 的家目录。它单独位于根分区上，而不是放在 `/home` 下，以保证 root 在 `/home` 未挂载或出现问题时仍能登录和修复系统。

**/usr** 是根目录之下**第二层只读数据层次**，存放所有用户可共享的静态程序、库和文档。它不是 “user” 的缩写，而是 “Unix System Resource”。`/usr/bin` 存放大多数用户命令，`/usr/sbin` 存放非启动必需的管理命令，`/usr/lib` 存放库文件，`/usr/share` 存放架构无关的共享数据（如文档、图标），`/usr/local` 则留给管理员手动安装本地软件。

**/var** 存放**在系统运行过程中会发生变化的数据**，如日志（`/var/log`）、邮件队列（`/var/mail`）、缓存（`/var/cache`）、锁文件（`/var/lock`）和假脱机文件（`/var/spool`）。`/var` 的引入正是为了把可变文件从 `/usr` 中隔离出来，使 `/usr` 可以安全地以只读方式挂载。

**/tmp** 存放程序运行时产生的临时文件。FHS 并不保证 `/tmp` 中的数据在重启后仍然存在，许多发行版会在启动时清理该目录，因此不应把需要保留的内容放在这里。

**/boot** 存放引导加载程序、内核镜像和 initrd 等启动所需文件。它通常是独立分区，内容在系统正常运行时不发生变化。

**/dev** 存放设备文件，代表系统中的硬件设备，如硬盘 `/dev/sda`、终端 `/dev/tty`、空设备 `/dev/null`。向设备文件读写，就是与对应硬件交互。

**/proc** 和 **/sys** 是内核导出的**虚拟文件系统**，并不占用磁盘空间。`/proc` 暴露进程和系统状态信息（如 `/proc/cpuinfo`、`/proc/meminfo`），`/sys` 提供设备驱动和内核对象的接口。严格来说，它们不属于 FHS 规定的目录，而是 Linux 特有的机制。

**/run** 存放本次启动以来的**易失性运行时数据**，如 PID 文件、Unix 套接字等，重启后内容消失。传统上 `/var/run` 承担这一角色，现在 `/var/run` 通常是指向 `/run` 的符号链接。

**/opt** 用于安装**附加的第三方软件包**，每个包通常拥有自己独立的子目录，便于整体删除或替换。

**/srv** 存放本机对外提供服务所用的数据，如 Web 站点的网页文件或 FTP 服务器的文件。

**/media** 和 **/mnt** 都是挂载点。`/media` 通常由系统自动用于可移动介质（U 盘、光盘）的挂载，`/mnt` 则留给管理员手动临时挂载文件系统。

### 重要目录之间的关系

**/bin、/sbin、/lib 与 /usr 的合并关系。** 传统上，`/bin`、`/sbin`、`/lib` 位于根分区，`/usr/bin`、`/usr/sbin`、`/usr/lib` 位于 `/usr` 层次，二者是分开的。现代主流发行版（Debian、Ubuntu、Fedora、openSUSE 等）普遍采用 **usrmerge** 方案：将 `/bin`、`/sbin`、`/lib` 替换为指向 `/usr/bin`、`/usr/sbin`、`/usr/lib` 的符号链接，实际文件全部归入 `/usr` 下。这样所有程序与库集中在同一棵子树中，既便于以只读方式保护系统文件，也便于在容器之间共享 `/usr`。因此在较新的系统上，`ls -l /` 看到的 `/bin` 是一个指向 `usr/bin` 的链接，而非独立目录。

**/usr 与 /var 的分工。** FHS 把目录树按“静态/可变”分开：`/usr` 存放不随系统运行而变化的静态数据，`/var` 存放会频繁写入的可变数据。历史上可变文件也曾放在 `/usr` 和 `/etc` 下，`/var` 层次的建立正是为了把可变文件隔离出来，使 `/usr` 可以只读挂载，并让静态文件与需要频繁备份的可变文件各自独立管理。

**/usr/local 与 /opt 的分工。** 两者都用于安装“非发行版包管理器提供”的软件，但定位不同。`/usr/local` 是**管理员手动编译安装**的软件层次，其内部结构与 `/usr` 镜像（`/usr/local/bin`、`/usr/local/lib` 等），适合从源码 `make install` 且遵循标准目录布局的软件；`/opt` 则用于**第三方打包的附加软件**，通常每个软件独占一个子目录，适合不遵循 `/usr` 布局、需要整体安装和整体移除的独立软件包。此外，`/usr/local` 对应的可变数据位于 `/var/local`，`/opt` 对应的可变数据位于 `/var/opt`，这一对应关系在 FHS 中有明确规定。

**/etc、/home 的“不可共享”属性。** 在 FHS 的分类中，`/etc` 是**不可共享且静态**的（配置属于本机，但不随运行频繁变化），`/home` 中的用户文件是**可共享但可变**的。正因为 `/etc` 是本机专属的，它不应放到网络共享上供多台机器共用；而 `/home` 中的文件虽然可变，却可以通过 NFS 等方式在多台主机之间共享。

### FHS 文件系统层次标准

FHS（Filesystem Hierarchy Standard）是定义类 Unix 系统中目录结构和目录内容的一套规范，它规定哪些目录是必需的、各自的用途是什么、最少应包含哪些内容，从而让软件开发者和系统管理员能够**预知文件应该放在哪里**。

FHS 的核心贡献是按两个维度对文件进行分类，并据此决定目录布局：

| 维度 | 含义 | 典型示例 |
|---|---|---|
| **可共享 vs 不可共享** | 可共享文件可存放在一台主机上供其他主机使用；不可共享文件仅限本机 | 可共享：`/usr/lib`、`/usr/share/doc`；不可共享：`/etc`、`/home` 中的用户专属文件 |
| **静态 vs 可变** | 静态文件不经管理员操作不会改变；可变文件在系统正常运行中会变化 | 静态：`/usr/bin`、`/usr/lib`、`/etc`；可变：`/var/mail`、`/run` 中的 PID 文件 |

这两个维度可以交叉：例如 `/var/mail` 是“可共享且可变”，`/etc` 是“不可共享且静态”。FHS 要求将不同属性的文件放在不同目录中，以便针对不同使用特征分别管理（例如静态文件可放在只读介质上、备份频率可以低于可变文件）。

在结构上，FHS 规定了**三个主要层次**：

1. **根文件系统 `/` 层次**：只包含启动、恢复和修复所必需的内容，保持最小化；
2. **`/usr` 层次**：存放可共享的只读用户程序和静态数据；
3. **`/var` 层次**：存放可变数据，与静态的 `/usr` 隔离。

FHS 是**指南性标准**，并非所有发行版在所有细节上都完全一致（例如 `/proc` 和 `/sys` 是 Linux 特有机制，不在 FHS 规范内）。但主流发行版在核心目录的用途上高度一致，因此学会一套目录结构，可以迁移到大多数 Linux 系统上使用。

## Linux 文件系统的实现原理

### VFS 虚拟文件系统

Linux 支持 ext4、XFS、Btrfs、FAT32、NTFS、NFS 等众多文件系统，它们内部的磁盘布局、元数据组织方式和分配策略各不相同。如果每个应用程序都要为每种文件系统写一套代码，系统将无法维护。**VFS（Virtual File System，虚拟文件系统）** 正是为了解决这一问题而存在的：它在内核中提供一个统一的抽象层，使 `open()`、`read()`、`write()`、`stat()` 等系统调用对所有文件系统表现一致，而具体的读写操作由底层文件系统的实现来完成。

VFS 的核心是一组**抽象对象模型**，主要包括四种对象：

**超级块（superblock）** 代表一个已挂载的文件系统实例，记录该文件系统的整体信息，如块大小、已用与空闲空间、根 inode 的位置等。每种文件系统提供自己的超级块操作函数，VFS 通过它们挂载、卸载和查询文件系统。

**inode 对象** 是文件系统中一个具体文件（或目录、设备等）在内存中的表示，封装了文件的元数据和指向数据块的索引信息。同一文件在磁盘上的 inode 会在需要时被读入内存，修改后再写回。

**dentry（目录项）对象** 是路径解析过程中一个名字到 inode 的缓存映射。VFS 维护一个 dentry 缓存（dcache），把路径中的每个分量（如 `/home/alice/docs` 中的 `home`、`alice`、`docs`）解析为对应的 dentry，从而快速从路径名定位到 inode。dentry 只存在于内存中，不写入磁盘，纯粹用于性能优化。

**file 对象** 代表一个进程打开文件的实例。每次调用 `open()` 获得一个文件描述符，内核就分配一个 file 对象，记录打开模式、当前读写位置以及与 dentry 的关联。多个进程可以打开同一个文件，各自拥有独立的 file 对象，但共享同一个 inode。

这四个对象之间的关系可以概括为：超级块管理文件系统整体，inode 描述单个文件实体，dentry 提供“名字→inode”的快速查找，file 记录一次打开会话的状态。一个 inode 可以被多个 dentry 指向（这正是硬链接的基础），而一个 dentry 在同一时刻只对应一个 inode。VFS 让上层应用完全不必关心底层是 ext4 还是 NFS——无论数据实际存放在本地磁盘还是远程服务器，系统调用的语义保持一致。

### Inode 与 Block

文件在磁盘上并不是连续存放的一整块，而是被划分为固定大小的 **block（块）**，分散存储在磁盘的不同位置。这样做的好处是避免外部碎片：如果文件必须连续存放，反复创建删除后磁盘上将留下大量无法利用的小空隙；按固定大小分块、非连续分配，则任何空闲块都可以被复用。

**inode（索引节点，index node）** 是文件系统用来追踪一个文件使用了哪些块的元数据结构。每个文件对应一个 inode，inode 中存储两类信息：一是**文件元数据**，包括文件类型、权限、所有者、大小、时间戳（访问、修改、inode 变更时间）等；二是**数据块的索引**，即该文件的数据存放在磁盘的哪些块中。inode 本身也存储在磁盘块中，通常以数组形式连续存放，**inode 号就是该数组的下标**，在同一个文件系统内唯一标识一个文件。

inode 如何索引数据块，决定了文件系统能支持多大的文件。经典方案采用**多级索引**：inode 中直接存放前若干个数据块的块号（**直接块**），适合小文件；当文件更大时，使用**一次间接块**，该块中存放的是一批数据块的块号；再大则使用**二次间接块**（间接块中存放一次间接块的块号）和**三次间接块**。这种层级结构与内存管理中的多级页表类似，使得 inode 本身保持较小，同时通过间接层支持远超直接块容量的大文件。

对用户而言，inode 的存在解释了几个常见现象：`df -i` 查看的是 **inode 使用量**，即使磁盘还有空间，inode 耗尽（大量小文件）也会导致无法创建新文件；`stat` 命令显示的 “Inode” 就是文件的 inode 号，“Links” 是硬链接计数；文件系统在格式化时就预先分配了固定数量的 inode，因此 inode 总数是有限的。

### 文件名与 Inode 的关系

一个关键事实是：**inode 中不存储文件名**。文件名保存在**目录**中，目录本质上是一种特殊文件，其内容是一张“文件名 → inode 号”的映射表。当用户访问 `/home/alice/report.txt` 时，内核的解析过程是：从根目录的 inode 出发，在根目录的数据块中找到 `home` 这个名字及其 inode 号，加载 `home` 的 inode，再在其中找到 `alice`，依此类推，最终在 `alice` 目录的数据块中找到 `report.txt` 对应的 inode 号，加载该 inode，取得数据块的索引，然后读取数据。

这一设计带来了几个重要推论。**重命名文件**（`mv` 同一文件系统内的文件）只改变目录中的名字映射，不移动数据，也不改变 inode，因此速度极快。**同一 inode 可以有多个文件名**，这正是硬链接的实现基础：多个目录项可以各自记录同一个 inode 号，inode 中的链接计数（link count）记录有多少个目录项指向它。**删除文件**（`unlink`）减少链接计数，只有当计数归零且没有进程打开该文件时，inode 和数据块才真正释放；在此之前，即使文件名已从目录中消失，仍可通过已打开的文件描述符继续访问数据。

文件名与 inode 的分离，把“人类可读的命名”和“文件系统的内部标识”解耦。名字可以随意更改而不触动数据，inode 则稳定地代表文件实体。这也意味着，仅凭文件名无法判断两个路径是否指向同一个文件——需要用 `ls -i` 或 `stat` 比较 inode 号。

### 硬链接与软链接

**硬链接**是给同一个 inode 增加一个新的目录项。用 `ln 源文件 新名字` 创建后，新旧两个名字地位完全对等，没有“原件”与“副本”之分：它们共享同一个 inode、同一组数据块、同一份权限与时间戳，inode 的链接计数加一。修改任一名字的内容，另一个名字立即可见；删除其中一个名字只减少链接计数，不影响另一个；只有当所有硬链接都被删除（且没有进程打开文件）时，数据才被回收。硬链接有两条硬性限制：**不能跨文件系统**，因为不同文件系统的 inode 编号独立编号、无法互认；**普通用户不能为目录创建硬链接**，因为目录硬链接会引入环，破坏目录树的树形结构。

**软链接（符号链接）** 则是一个**独立的新文件**，拥有自己的 inode 和数据块（或内联数据），其内容不是文件数据，而是**目标路径的字符串**。用 `ln -s 目标 链接名` 创建。访问软链接时，内核读取其中的路径字符串，再重新解析该路径来定位目标。因此软链接的 inode 号与目标不同，二者是两个不同的文件。软链接可以指向目录，可以跨文件系统，也可以指向一个不存在的路径（产生“悬空链接”），此时访问会报错。删除软链接本身不会影响目标；删除目标则导致软链接失效，但如果之后在相同路径重建目标，软链接会“恢复”可用，因为它保存的是路径而非 inode。

二者的本质区别可以归结为一句话：**硬链接共享 inode，软链接拥有自己的 inode 并保存路径**。硬链接是“同一个文件的另一个名字”，软链接是“指向某个路径的指示器”。判断方式也很直接：`ls -i` 看 inode 号是否相同，`ls -l` 看类型标识是否为 `l` 以及是否有 `->` 指向。

### 常见文件系统类型

VFS 提供统一接口，底层文件系统则各有取舍。Linux 上常见的类型包括：

- **ext4** 是第四代扩展文件系统，也是多数发行版的默认选择。它成熟、稳定、工具链完善，支持日志（journaling）以保证崩溃后的一致性，最大支持 1 EiB 分区和 16 TiB 单文件，采用延迟分配和多块分配来提升性能。在通用桌面与服务器场景中，ext4 是兼容性和维护成本最低的选项，EC4 也常被描述为“多数用户的标准选择”。
- **XFS** 是高性能的 64 位日志文件系统，2001 年移植到 Linux 内核。它在**大文件顺序 I/O 和高并发写入**场景中表现突出，写入时 CPU 开销低，适合视频存储、日志聚合、科学计算等大吞吐负载。XFS 支持在线扩容，但不支持收缩，因此容量规划宜“先规划后扩展”。
- **Btrfs** 是基于 B 树和写时复制（CoW）的现代文件系统，提供**快照、子卷、数据与元数据校验和自修复、内置 RAID** 等高级特性。它在开发环境的混合负载中表现均衡，适合需要快照与数据保护的场景，但高级特性也带来更高的运维复杂度。
- **ZFS** 同样提供快照、校验、池化管理等企业级特性，但 CPU 开销显著，在消费级硬件上可能占用大量计算资源，更适合专用存储服务器而非通用笔记本。
- **FAT32 / exFAT / NTFS** 主要用于**跨平台兼容**。FAT32 几乎所有系统都能读写，但不支持大于 4 GiB 的单文件且无日志；exFAT 解除了大小限制，适合 U 盘和 SD 卡；NTFS 是 Windows 原生文件系统，Linux 上通常通过内核驱动或 FUSE 访问，作为数据盘可与 Windows 共享，但不建议作为 Linux 系统盘。此外，**NFS** 和 **CIFS/SMB** 是网络文件系统，通过 VFS 接入后，远程文件在本地目录树中呈现为普通文件；`/proc` 和 `/sys` 则是伪文件系统，不存储实际数据，而是内核数据结构的窗口。

选择文件系统时，通用场景优先 ext4；大文件高吞吐选 XFS；需要快照、校验或子卷管理选 Btrfs（需具备相应运维经验）；跨平台移动存储选 exFAT 或 NTFS。VFS 的存在使得这一选择在很大程度上是**部署决策**而非**编程决策**——应用代码无需因文件系统类型而改变。

## Linux 启动流程

### BIOS / UEFI

按下电源键后，CPU 从固定地址开始执行固件代码，启动流程的第一步由主板固件完成。传统 BIOS 和现代 UEFI 是两代固件标准，它们的引导方式有本质区别。

**BIOS（Basic Input/Output System）** 是较早的固件接口。上电后它先执行加电自检（POST），检测 CPU、内存、显卡、键盘等基本硬件，然后按照 CMOS 中设置的启动顺序，依次尝试从软盘、硬盘、光驱、U 盘等设备引导。对于硬盘，BIOS 读取该磁盘的第一个扇区——**主引导记录（MBR，共 512 字节）**，其中前 446 字节是引导代码，随后是分区表，最后两字节是签名 `0x55AA`。BIOS 把控制权交给这 446 字节的引导代码，由它继续加载后续的引导程序。MBR 方案的限制很明显：引导代码只有 446 字节，分区表只能描述四个主分区，且磁盘容量受 2 TiB 限制。

**UEFI（Unified Extensible Firmware Interface）** 是 BIOS 的替代标准。它不再依赖 MBR 中的一小段代码，而是从磁盘上的 **EFI 系统分区（ESP）** 中直接加载 `.efi` 格式的引导程序。ESP 是一个 FAT32 分区，通常挂载在 `/boot/efi`，其中存放 `EFI/` 目录下的引导应用，例如 `EFI/ubuntu/grubx64.efi` 或用于 Secure Boot 的 `shimx64.efi`。UEFI 固件维护一张启动项表（NVRAM 中的 BootOrder），记录每个操作系统的引导程序路径，启动时按顺序尝试。UEFI 支持 GPT 分区表（突破 2 TiB 限制、主分区数量大幅增加）、图形化设置界面、Secure Boot（验证引导程序的数字签名，防止未签名代码在启动早期运行）以及更快的启动速度。

两者的共同点是：固件只负责找到并启动**下一阶段的引导程序**，本身并不加载 Linux 内核。这一阶段的核心任务是完成硬件初始化、确定从哪个设备引导，并把控制权交接出去。

### Bootloader（GRUB）

**Bootloader（引导加载程序）** 是固件与内核之间的桥梁，负责把 Linux 内核和初始内存盘加载到内存并移交控制权。Linux 上最常用的引导程序是 **GRUB（GRUB 2）**，此外还有 systemd-boot、LILO（已基本淘汰）、Syslinux 等。

在 BIOS + MBR 方案下，GRUB 分阶段加载：**stage1** 位于 MBR 的 446 字节引导代码中，功能极简，只负责把控制权交给 **stage1.5**；stage1.5 存放在 MBR 之后、第一个分区之前的空隙（gap）中，包含读取文件系统所需的驱动，使 GRUB 能够识别 `/boot` 所在分区；随后加载位于 `/boot/grub/` 下的 **stage2**，它才是完整的 GRUB 主体。在 UEFI 方案下，GRUB 以 `grubx64.efi`（或经 shim 中转）的形式直接从 ESP 加载，不再需要 MBR 分阶段机制。

GRUB 的主体启动后会读取配置文件 `/boot/grub/grub.cfg`（不同发行版路径略有差异），其中定义了菜单项、默认启动项、超时时间、内核命令行参数以及每个菜单项对应的内核与 initramfs 路径。用户可以在启动菜单中按 `e` 临时编辑内核参数（例如进入单用户模式或修改 `root=` 参数），按 `c` 进入 GRUB 命令行。选定菜单项后，GRUB 执行 `linux` 命令加载内核镜像（`vmlinuz-*`），执行 `initrd` 命令加载初始内存盘（`initramfs-*` 或 `initrd.img-*`），然后跳转到内核入口点。

GRUB 的配置通常不直接手改 `grub.cfg`，而是修改 `/etc/default/grub`（默认项、超时、内核参数）和 `/etc/grub.d/` 下的脚本，再运行 `update-grub`（Debian/Ubuntu）或 `grub2-mkconfig`（RHEL 系）重新生成。理解这一点可以避免“改了配置却不生效”的常见困惑。

### Linux Kernel 加载

内核镜像（`vmlinuz`）是一个压缩的、自解压的可执行文件。GRUB 把它和 initramfs 加载到内存后跳转过去，内核先解压自身，然后开始初始化。

内核启动初期的工作按顺序大致是：设置 CPU 与内存管理（建立页表、初始化物理内存分配器）、初始化调度器、注册中断与时钟、探测并初始化各子系统（ACPI、PCI、块设备、网络等）、加载内建驱动。内核命令行参数（即 GRUB 中 `linux` 行 `vmlinuz` 之后的内容，如 `root=UUID=... ro quiet splash`）在这一阶段被解析，决定根文件系统位置、是否进入紧急模式、日志级别等行为。

一个关键问题是：**内核需要挂载根文件系统，但访问根文件系统所需的驱动（如磁盘控制器、RAID、LVM、加密卷、网络存储的驱动）可能并未编译进内核，而是以模块形式存在**。如果内核在挂载根之前就需要这些模块，而模块又存放在尚未挂载的根文件系统上，就形成了“先有鸡还是先有蛋”的困境。**initramfs** 正是为了解决这个困境而引入的中间层。

内核完成基本初始化后，会解压 initramfs 到内存中的 tmpfs，并执行其中的 `/init` 程序（早期使用 initrd 时是 `/linuxrc`），把后续的根文件系统挂载工作交给它。

### Initramfs 初始化

**initramfs（initial RAM filesystem）** 是一个 cpio 格式的归档文件，内核在启动时把它解压到内存中的临时文件系统（tmpfs），其内容是一套最小化的目录结构、驱动模块和初始化脚本。它不占用磁盘上的固定分区，而是随内核一起被加载，因此可以独立于根文件系统存在。

initramfs 中的 `/init` 脚本（或程序）承担以下任务：加载挂载根文件系统所需的存储驱动（如 `ahci`、`nvme`、`virtio_blk`）、组装 RAID 与 LVM 卷、解锁 LUKS 加密卷（此时可能需要用户输入密码）、处理网络根（NFS root）的配置，然后按照内核命令行给出的 `root=` 参数找到真正的根文件系统并挂载它。

根文件系统挂载成功后，initramfs 执行 **`switch_root`**（或 `pivot_root`），把根目录切换到真正的根文件系统，并启动其中的 `/sbin/init`（在现代发行版上通常是 systemd）。此后，initramfs 占用的内存被释放，系统进入真正的用户空间启动阶段。

initramfs 由发行版的工具生成，例如 Debian/Ubuntu 使用 `update-initramfs -u`，RHEL 系使用 `dracut -f`。当更换存储控制器、修改 LVM/RAID/加密配置或升级内核后，若忘记更新 initramfs，系统可能在启动时找不到根文件系统而进入紧急 shell——这是实际运维中常见的一类启动故障。

### systemd 启动

systemd 是现代主流发行版的初始化系统，作为 PID 1 运行，负责启动并管理系统中的所有服务与资源。它接管控制权后，读取 `/etc/systemd/system/` 与 `/lib/systemd/system/`（或 `/usr/lib/systemd/system/`）下的 **unit** 文件，按照依赖关系启动系统。

systemd 的核心概念是 **unit**，常见类型包括：`.service`（服务）、`.target`（目标，相当于一组 unit 的集合）、`.socket`（套接字激活）、`.mount`（挂载点）、`.timer`（定时器）、`.device`（设备）。每个 unit 文件描述其启动命令、依赖关系（`Requires`、`Wants`、`After`、`Before`）和启动条件。systemd 根据这些依赖构建依赖图，**并行启动**互不依赖的服务，而不是像传统 SysV init 那样按脚本顺序串行执行，这是启动速度显著提升的主要原因之一。

systemd 的启动终点由 **default.target** 决定，它通常是指向 `multi-user.target`（多用户命令行）或 `graphical.target`（图形界面）的符号链接。传统运行级别与 target 的对应关系大致是：`runlevel 3` 对应 `multi-user.target`，`runlevel 5` 对应 `graphical.target`，`runlevel 1` 对应 `rescue.target`。可以用 `systemctl get-default` 查看默认 target，用 `systemctl set-default` 修改。

除并行启动外，systemd 还提供**按需启动**与**套接字激活**：服务不必在开机时全部拉起，可以在首次有客户端连接其 socket 时才启动（`.socket` unit），从而缩短启动时间并节省资源。systemd 还统一管理日志（journald）、挂载、定时任务（timer 取代 cron 的许多用法）和登录会话（logind），使启动流程的各个环节集中在一套框架内。

### 系统进入运行状态

当 `default.target` 所依赖的所有 unit 都达到活动状态后，系统进入正常运行状态。若默认目标是 `graphical.target`，systemd 会启动显示管理器（如 GDM、SDDM、LightDM），由它呈现登录界面，用户登录后进入桌面会话；若默认目标是 `multi-user.target`，systemd 则在各虚拟终端上启动 `getty`，提供文本登录提示符。无论哪种方式，用户登录后获得一个 Shell 或桌面会话，启动流程至此完成。

启动过程中的耗时可以用 **`systemd-analyze`** 系列命令分析：`systemd-analyze` 显示固件、引导程序、内核、用户空间各阶段的总耗时；`systemd-analyze blame` 按耗时排序列出各服务的启动时间；`systemd-analyze critical-chain` 展示关键路径上前后依赖的服务链。这些工具是定位“开机慢”问题的起点：若固件阶段耗时长，问题可能在 BIOS/UEFI 设置或硬件自检；若内核阶段长，可能与驱动初始化或硬件探测有关；若用户空间长，则需检查具体服务的依赖与超时。

排障时还需要知道几个关键入口：启动过程中按 `Esc` 或查看 `journalctl -b` 可看到本次启动的完整日志；在 GRUB 菜单中给内核参数追加 `systemd.unit=rescue.target` 或 `single` 可进入救援/单用户模式；追加 `rd.break` 可在 initramfs 阶段中断，用于修复根文件系统或重置密码；追加 `systemd.log_level=debug` 可提高日志详细程度。掌握这些入口，结合对“固件 → 引导程序 → 内核 → initramfs → systemd → 运行状态”这一链条的理解，就能把启动故障定位到具体阶段，而不是笼统地“开不了机”。

整个启动流程可以概括为一条清晰的接力链：**固件（BIOS/UEFI）完成硬件初始化并找到引导程序 → Bootloader（GRUB）加载内核与 initramfs → 内核初始化子系统并解压 initramfs → initramfs 加载必要驱动、挂载真正的根文件系统并切换根 → systemd 作为 PID 1 按依赖图并行启动各 unit → 到达 default.target，系统进入可用状态**。每一阶段都把控制权交给下一阶段，任何一环出错都会在后续阶段表现为“卡住”或“进入紧急模式”，因此排障的关键是判断故障发生在哪一环。
