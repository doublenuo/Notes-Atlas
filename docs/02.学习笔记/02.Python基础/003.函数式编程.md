# Python 函数式编程到底该怎么用？从 lambda 到装饰器一次讲清楚

先交代一段背景，它决定了你对 Python 函数式该抱什么态度。上世纪 90 年代初，一位怀念 Lisp 的程序员给 Python 提交了 `lambda`、`map`、`filter`、`reduce` 四个函数的补丁，Guido van Rossum 收下了，但心里一直不太喜欢。2005 年他公开说想在 Python 3 里把这四个全删掉，最后只有 `reduce` 被流放进了 `functools`，其余三个留了下来。**理解了这段「半推半就」的历史，你就理解了 Python 对函数式的立场：能用，但从来不鼓励你把它当信仰。**

这篇文章把散落在 Python 里的函数式工具串成一条线。适合写过不少 Python、但对 lambda、闭包、装饰器总觉得「会用但说不清原理」的人。读完你能想明白三件事：这些工具各自怎么用、背后到底发生了什么、以及实际项目里什么时候该上、什么时候该收手。


## 一、函数是一等对象：Python 函数式的地基

函数式编程有个前提——**函数得能和整数、字符串一样，被当作普通值来传递**。在 Python 里这是天生成立的：函数是一等对象（first-class object），你可以把它塞进变量、当作参数传出去、或者作为返回值拿回来。

```python
def add(a, b):
    return a + b

# 塞进变量
f = add
print(f(1, 2))            # 3

# 当作参数传出去
def apply(func, x, y):
    return func(x, y)

print(apply(add, 3, 4))   # 7

# 当作返回值拿回来
def make_adder(n):
    def adder(x):
        return x + n
    return adder

add5 = make_adder(5)
print(add5(10))           # 15
```

接受函数作参数、或返回函数的函数，就叫**高阶函数**。你天天在用的 `sorted(key=...)`、`map`、装饰器，本质都是它。这是整篇文章的地基，后面所有东西都建立在「函数能当值传」这一点上。

**每个函数都是个货真价实的对象**，身上挂着一串元信息。看一眼你就信了：

```python
def add(a, b=10):
    "两个数相加"
    return a + b

print(add.__name__)              # add
print(add.__doc__)               # 两个数相加
print(add.__defaults__)          # (10,)
print(add.__code__.co_argcount)  # 2
print(add.__code__.co_varnames)  # ('a', 'b')
```

**CPython 细节①**：`__code__` 指向一个**代码对象**，里面存的是函数编译后的**字节码**和常量表；`__defaults__` 存的是默认参数值。平时你不会碰它们，但讲到装饰器时你会看到，`functools.wraps` 干的事，无非就是把这一串属性从原函数拷到新函数上。

### lambda：一句话的匿名函数

`lambda` 是个**只能包含一个表达式**的匿名函数，语法 `lambda 参数: 表达式`，返回的就是表达式的值。它正确的用法，是「一句话能写完、且只用一次」的小函数：

```python
add = lambda a, b: a + b
print(add(2, 3))   # 5

nums = [3, 1, 2]
print(sorted(nums, key=lambda x: -x))   # [3, 2, 1]  按降序
```

一旦逻辑复杂到需要**赋值语句、多条语句、分支嵌套**，lambda 就撑不住了——它天生写不了赋值：

```python
# 这是语法错误：lambda 里不能写赋值语句
# f = lambda x: y = x + 1   # SyntaxError: cannot assign to lambda
```

```python
# 这种一行塞不下的逻辑，写成 def 更体面
def adjust(x):
    return x + 1 if x > 0 else x - 1
```

**什么时候该收手**：lambda 没名字、没文档，出错时 traceback 里只剩一个 `<lambda>`，排查起来比命名函数难受得多。所以一条经验——**会复用的、逻辑稍长的，一律 `def`**；lambda 只留给真正的一次性小函数。闭包行为上 lambda 和 def 一模一样，差别只在可读性和可调试性。


## 二、推导式与生成器：Python 式的「函数式」

如果说 lambda/map/filter 是从 Lisp 借来的舶来品，那**推导式（comprehension）就是 Python 自己长出来的答案**。Guido 当年敢说想砍掉 map/filter，底气就是「这些用推导式都能写，而且更好读」。

### 推导式：一行构造容器

```python
squares = [x * x for x in range(5)]
print(squares)   # [0, 1, 4, 9, 16]

evens = [x for x in range(10) if x % 2 == 0]
print(evens)     # [0, 2, 4, 6, 8]

d = {x: x * x for x in range(4)}
print(d)         # {0: 0, 1: 1, 2: 4, 3: 9}

s = {x % 3 for x in range(10)}
print(s)         # {0, 1, 2}
```

两个细节值得记住。一是**作用域**：Python 3 里推导式有自己的作用域，循环变量不会漏出去污染外层。

```python
x = 10
lst = [x * x for x in range(3)]
print(lst)   # [0, 1, 4]
print(x)     # 10  外面的 x 没被覆盖
```

二是**嵌套边界**：一层嵌套还看得过去，两层以上就该拆成普通循环了。

```python
matrix = [[1, 2], [3, 4]]
flat = [v for row in matrix for v in row]
print(flat)   # [1, 2, 3, 4]
```

### 生成器表达式：懒一点，省一车内存

把方括号 `[]` 换成圆括号 `()`，就得到**生成器表达式**。它和列表推导式的差别只有一个字——**懒**：不一次性把所有结果算出来，而是用到谁才算谁。

```python
import sys

squares_list = [x * x for x in range(10 ** 6)]
squares_gen = (x * x for x in range(10 ** 6))

print(sys.getsizeof(squares_list))   # 8448728  约 8MB
print(sys.getsizeof(squares_gen))    # 200      几乎不占
```

一百万个平方，列表一把全算出来吃掉 8MB，生成器只占 200 字节。差别就是「立即算」和「按需算」。

但「懒」是有代价的——**生成器只能遍历一次，走完就没了**。

```python
g = (x * x for x in range(3))
print(list(g))   # [0, 1, 4]  第一次正常
print(list(g))   # []         第二次空了！不是 bug，是特性
```

**CPython 细节②：生成器是个「能冻住的栈帧」**。调用生成器函数时，函数体**根本不执行**，只返回一个生成器对象；每次 `next()` 才让它跑到下一个 `yield`，然后把整个**栈帧**（局部变量、执行位置）原地冻住。源码里生成器对象的核心字段，就是一个攥在手里的帧 `gi_frame`。

```python
def gen():
    x = 1
    yield x
    x += 1
    yield x

g = gen()
print(next(g))                 # 1
print(g.gi_frame.f_locals)     # {'x': 1}  帧被冻住，x 还留着
print(next(g))                 # 2
```

想通「冻住的栈帧」，你就顺带想通了协程——`asyncio` 里的 `async def` 和生成器用的是同一套「暂停/恢复」机制。

### 迭代器 vs 可迭代对象

这两个词常被混着用，其实差一层：

- **可迭代对象**：实现了 `__iter__`，能被 `for` 遍历，如 `list`、`str`、`tuple`。它每次 `iter()` 都吐出一个**新的**迭代器，所以能反复遍历。
- **迭代器**：实现了 `__iter__` **和** `__next__`，是「正在遍历中」的那个对象。生成器、`iter(list)` 的返回值，都是迭代器。

```python
lst = [1, 2, 3]
print(hasattr(lst, "__iter__"))   # True   可迭代
print(hasattr(lst, "__next__"))   # False  但不是迭代器

it = iter(lst)
print(hasattr(it, "__next__"))    # True

print(next(it))   # 1
print(next(it))   # 2
print(next(it))   # 3
# print(next(it)) # StopIteration  取完抛异常，for 循环就是这么终止的
```

`for` 循环的内部动作就是两件：先 `iter()` 拿到迭代器，再反复 `next()` 直到 `StopIteration`。所以你也可以手写 `next()` 来手动控制遍历节奏。

### 推导式 vs map/filter

Guido 的立场很明确：能用推导式写清楚的，就别上 map/filter。

```python
nums = [1, 2, 3, 4]

print([x * 2 for x in nums])                     # [2, 4, 6, 8]
print(list(map(lambda x: x * 2, nums)))          # [2, 4, 6, 8]

print([x for x in nums if x % 2 == 0])           # [2, 4]
print(list(filter(lambda x: x % 2 == 0, nums)))  # [2, 4]
```

**对比表①**：

| 特性 | 列表推导式 | map / filter | 生成器表达式 |
|------|-----------|-------------|-------------|
| 返回类型 | list | map/filter 对象 | generator |
| 是否惰性 | ❌ 立即求值 | ✅ | ✅ |
| 内存占用 | 一次性全部 | 按需 | 按需 |
| 可遍历次数 | 多次 | 一次 | 一次 |
| 可读性 | 高（带条件尤其） | 中 | 高 |

一个例外：当映射函数是**现成函数**（`str`、`int` 这种）时，`map` 反而更干净，因为不用多写一层 lambda。

```python
print(list(map(str, [1, 2, 3])))   # ['1', '2', '3']  这里 map 更直接
```

## 三、map、filter、reduce 与 functools：标准库里的函数式工具

### map 与 filter

`map(func, iterable)` 对每个元素套一遍 `func`；`filter(func, iterable)` 留下 `func` 返回真值的元素。两者返回的都是**惰性对象**，得 `list()` 包一下才看得见。

```python
print(list(map(str, [1, 2, 3])))                      # ['1', '2', '3']
print(list(filter(lambda x: x % 2 == 0, range(6))))   # [0, 2, 4]
```

### reduce：一个被「流放」的函数

`reduce(func, iterable)` 把序列**两两归约**成一个值。它曾经是内置函数，Python 3 里被移进了 `functools`。

```python
from functools import reduce
print(reduce(lambda a, b: a + b, [1, 2, 3, 4]))   # 10
```

为什么被流放？Guido 自己的解释很直白，他说 reduce 是这四个函数里他最讨厌的一个：

> 除了少数 `+` 或 `*` 的例子，几乎每次我看到一个参数非平凡的 `reduce()` 调用，都得掏出纸笔推演一遍喂进去的到底是什么，才能搞懂它想干嘛。

换句话说，reduce 的可读性太差了。他还补过一刀，说 `functools` 这个模块就是「放我不太在乎的东西的地方」。所以现实里 reduce 用得极少——大多数归约都有更直白的写法。

```python
nums = [1, 2, 3, 4]
print(sum(nums))   # 10  比 reduce 清楚多了
```

### functools.partial：先把参数钉死

`partial` 把函数的部分参数**预先固定**，生成一个新函数。适合「同一个函数总是带同一组参数」的场景。

```python
from functools import partial

def power(base, exp):
    return base ** exp

square = partial(power, exp=2)
cube = partial(power, exp=3)

print(square(5))   # 25
print(cube(5))     # 125
```

### operator.itemgetter / attrgetter：给 lambda 找个替身

`operator` 模块把「取下标」「取属性」这类常用动作包装成函数，专门替代那些「其实只想写个 `lambda x: x["score"]`」的场景。

```python
from operator import itemgetter

students = [
    {"name": "a", "score": 90},
    {"name": "b", "score": 85},
]

print(sorted(students, key=itemgetter("score")))
# [{'name': 'b', 'score': 85}, {'name': 'a', 'score': 90}]

print(sorted(students, key=itemgetter("score"), reverse=True)[0])
# {'name': 'a', 'score': 90}
```

`itemgetter("score")` 等价于 `lambda d: d["score"]`，但更快、更清晰。在 `sorted`、`min`/`max`、`groupby` 里尤其常用。


## 四、闭包与装饰器：函数式的进阶用法

### 闭包：函数记住了一个变量

函数里再定义函数，内层函数**记住了外层函数的局部变量**，即使外层函数已经返回，内层照样能访问——这就是闭包。

```python
def outer(x):
    def inner(y):
        return x + y
    return inner

f = outer(10)
print(f(5))   # 15  外层都返回了，inner 还记得 x=10
```

**CPython 细节③：闭包存在 cell 里**。被闭包捕获的变量不是普通局部变量，而是被挪进一个叫 **cell** 的结构。函数的 `__closure__` 就是一个 cell 元组，`cell_contents` 能直接看到被捕获的值。

```python
print(f.__closure__)                    # (<cell ...: int object ...>,)
print(f.__closure__[0].cell_contents)   # 10
```

搞清楚 cell 的存在，下面两个坑就都好解释了。

### 误区一：循环里的闭包，全都记住最后一个值

```python
funcs = []
for i in range(3):
    funcs.append(lambda: i)   # 以为每个 lambda 记住了自己的 i

print([f() for f in funcs])   # [2, 2, 2]  全是 2！
```

原因不是 bug，而是**延迟绑定（late binding）**：三个 lambda 闭包了**同一个 cell 里的 `i`**，而它们是在调用时才去 cell 里取值。循环跑完 `i == 2`，所以谁都读到 2。

反直觉的是，这个行为**恰恰是特性**。想想计数器就明白了：

```python
def counter():
    count = 0
    def inc():
        nonlocal count
        count += 1
        return count
    return inc

c = counter()
print(c(), c(), c())   # 1 2 3
```

如果闭包是「按值捕获」，每次调用都复制一份 `count`，这个模式就废了。所以延迟绑定不是设计失误，只是它在一个循环里看起来像陷阱。

修复方式很经典——用默认参数在**定义时**就把值钉死（默认参数是定义时求值的）：

```python
funcs = [lambda j=i: j for i in range(3)]
print([f() for f in funcs])   # [0, 1, 2]  这次对了
```

### nonlocal：想改外层变量，得先声明

闭包里**读**外层变量没问题；想**改**它，必须写 `nonlocal`，否则 Python 会把它当新局部变量，直接报 `UnboundLocalError`。

```python
def counter():
    n = 0
    def inc():
        nonlocal n    # 声明 n 是外层变量
        n += 1
        return n
    return inc

c = counter()
print(c(), c(), c())   # 1 2 3  状态保存在闭包里
```

`nonlocal` 只作用于**最近一层的封闭作用域**，不跨到模块全局（改全局用 `global`）。没写 `nonlocal` 的 `n += 1` 会直接报错，因为「读 + 赋值」同时出现时，Python 默认把 `n` 当成本函数的局部变量。

### 装饰器：给函数套一层外壳

装饰器就是一个**接收函数、返回新函数**的高阶函数，用来在不改原函数的前提下，给它加一层行为——日志、计时、鉴权、缓存，都靠它。

```python
import functools
import time

def timer(fn):
    @functools.wraps(fn)
    def wrapper(*args, **kwargs):
        start = time.perf_counter()
        result = fn(*args, **kwargs)
        print(f"{fn.__name__} 耗时 {time.perf_counter() - start:.4f}s")
        return result
    return wrapper

@timer
def slow_add(a, b):
    return a + b

print(slow_add(1, 2))
# slow_add 耗时 0.0000s
# 3
```

**误区二：漏写 `@functools.wraps` 会丢元信息**。

```python
import functools

def no_wraps(fn):
    def wrapper(*args, **kwargs):
        return fn(*args, **kwargs)
    return wrapper

def with_wraps(fn):
    @functools.wraps(fn)
    def wrapper(*args, **kwargs):
        return fn(*args, **kwargs)
    return wrapper

@no_wraps
def foo():
    "foo 的文档"
    pass

@with_wraps
def bar():
    "bar 的文档"
    pass

print(foo.__name__, repr(foo.__doc__))   # wrapper None  名字和文档都丢了
print(bar.__name__, repr(bar.__doc__))   # bar 'bar 的文档'
```

原因回到第一节：装饰器返回的是 `wrapper`，它的 `__name__`/`__doc__` 自然是 wrapper 自己的。`wraps` 干的事，就是把原函数的元信息复制过来（内部是 `functools.update_wrapper`）。**写装饰器默认就加 `@functools.wraps(fn)`**，否则日志、文档、调试全乱套。

### 带参数的装饰器：再包一层

装饰器本身要收参数时，得**套三层**：最外层收参数，返回真正的装饰器。

```python
def repeat(n):
    def decorator(fn):
        @functools.wraps(fn)
        def wrapper(*args, **kwargs):
            result = None
            for _ in range(n):
                result = fn(*args, **kwargs)
            return result
        return wrapper
    return decorator

@repeat(3)
def hello():
    print("hi")

hello()
# hi
# hi
# hi
```

`@repeat(3)` 其实就是 `hello = repeat(3)(hello)`：先 `repeat(3)` 拿到 `decorator`，再用它装饰 `hello`。三层看着绕，逻辑就这一句。

### 类装饰器：需要记状态时

装饰器不一定得是函数，类只要实现了 `__call__` 也能当装饰器，适合需要**维护状态**（比如计数）的场景。

```python
class CountCalls:
    def __init__(self, fn):
        self.fn = fn
        self.calls = 0
    def __call__(self, *args, **kwargs):
        self.calls += 1
        return self.fn(*args, **kwargs)

@CountCalls
def greet(name):
    return f"hi {name}"

print(greet("bob"))   # hi bob
print(greet("amy"))   # hi amy
print(greet.calls)    # 2
```

简单装饰器用函数，要记状态、逻辑复杂时用类，选哪个看复杂度，不是看谁更高级。

### lru_cache：现成的结果缓存

`functools.lru_cache` 是官方写好的缓存装饰器：按参数缓存函数结果，同样参数下次直接返回缓存，不重算。对递归、慢计算是神器。

```python
@functools.lru_cache(maxsize=None)
def fib(n):
    return n if n < 2 else fib(n - 1) + fib(n - 2)

print(fib(10))   # 55
print(fib.cache_info())
# CacheInfo(hits=8, misses=11, maxsize=None, currsize=11)
```

**CPython 细节④：缓存键怎么造**。`lru_cache` 用**参数元组当 key** 去查字典，所以要求**所有参数可哈希**——传列表、字典这种可变对象会直接报错。

```python
@functools.lru_cache(maxsize=128)
def f(x):
    return x

# f([1, 2])   # TypeError: unhashable type: 'list'
```

两个参数要搞清：`maxsize` 是**最多缓存多少条**，超出后按 LRU（最近最少使用）淘汰最久没用的；`maxsize=None` 表示无限缓存，`128` 是常见默认。因为按参数缓存，**结果会随环境变的函数**（读文件、读当前时间）千万别用它，否则会拿到过期答案。

## 五、纯函数、副作用与选型：什么时候该用函数式

### 纯函数与副作用

- **纯函数**：同样的输入永远得到同样的输出，且**不修改外部状态**。`add`、`sum`、`sorted`（返回新列表）都是。
- **副作用**：函数里改了外部变量、写了文件、发了请求、打印了内容，都算。

```python
def add(a, b):
    return a + b     # 纯函数

total = 0
def accumulate(x):   # 有副作用：改了全局状态
    global total
    total += x
    return total

print(add(1, 2))       # 3
print(accumulate(3))   # 3
print(accumulate(4))   # 7  结果依赖历史，不是纯函数
```

纯函数的好处是实在的：**好测试**（不用搭一堆环境）、**能缓存**（同参同果，`lru_cache` 就是靠这个）、**易并行**（互不干扰）。但真实项目里副作用**躲不掉**——写库、发请求、操作数据库都是副作用。真正该做的，是**把纯函数和副作用分开**：纯的部分集中起来好测，副作用收敛到边界。

### 不可变性与函数式的关系

函数式强调**数据不可变**——创建后不改，而是产生新数据。这正好和 Python 的不可变类型对上：`tuple`、`str`、`frozenset` 天然适合函数式，`list`、`dict` 原地改就是引入副作用。

```python
nums = [3, 1, 2]

sorted_nums = sorted(nums)   # 函数式：不原地改，返回新对象
print(nums)                  # [3, 1, 2]  原列表没动
print(sorted_nums)           # [1, 2, 3]

nums.sort()                  # 非函数式：原地排序，有副作用
print(nums)                  # [1, 2, 3]  原列表被改了
```

但别走极端——**Python 不是纯函数式语言**。它没有强制不可变，也没有 Haskell 的自动柯里化、模式匹配。Python 对函数式的态度，从开头那段历史就定了调：**借函数式的「思想」（纯函数、少副作用、数据管道），但不追求「写纯函数式代码」**。

### 什么时候用，什么时候收手

**适合函数式的场景**：

- **数据转换管道**：一批数据经 `map`/`filter`/推导式一步步变换，清晰、无中间状态。
- **排序、分组、查找的 `key`**：`sorted(..., key=itemgetter(...))` 这类。
- **横切逻辑**：日志、计时、鉴权、缓存——装饰器的主场。
- **纯计算缓存**：`lru_cache`。

**不适合的场景**：

- **复杂状态机**：状态多、跳转复杂时，硬写无副作用会很别扭，不如用对象封装状态。
- **需要清晰调试栈**：过度嵌套的 lambda、推导式会让 traceback 难读。
- **团队不熟函数式**：可读性是写给团队看的，不是给自己炫技的。

**对比表②**：

| 维度 | 函数式 | 面向对象 | 过程式 |
|------|--------|---------|--------|
| 核心抽象 | 纯函数 | 对象与消息 | 步骤与流程 |
| 状态管理 | 尽量不可变 | 封装在对象内 | 全局/局部变量 |
| 典型场景 | 数据转换、缓存、装饰器 | 领域建模、GUI、插件 | 脚本、一次性流程 |
| 复用方式 | 函数组合 | 继承/组合 | 抽函数 |
| 测试难度 | 低（纯函数好测） | 中（要 mock） | 中（依赖执行顺序） |

这三种风格**不是非此即彼**。真实项目几乎都是混着用：用类组织状态，方法内部用函数式写数据转换，入口用过程式串流程。关键是在合适的地方用合适的工具——这也正是 Python 自己几十年来对待函数式的态度。

## 小结

回头看这条主线：**函数是对象 → 用推导式/生成器做数据变换 → 用闭包/装饰器复用行为 → 用纯函数的思想做选型**。三句话收尾：

1. **函数式在 Python 里是工具，不是教条**——Guido 本人就这个态度。
2. **闭包、生成器、装饰器的坑，几乎都源于「惰性」或「共享状态」**：理解 cell、理解生成器只能遍历一次，就能避开大半。
3. **写装饰器默认加 `@functools.wraps`**，用 `lru_cache` 记得参数要可哈希、函数要纯。

### 几个常见问题

**Q1：lambda 和 def 到底用哪个？**
一句话能写完、只用一次用 `lambda`；要复用、要文档、逻辑稍长的，一律 `def`。可读性优先。

**Q2：循环里创建闭包为什么全是最后一个值？**
闭包捕获的是**变量**（cell），不是值；lambda 调用时才去 cell 里取，循环结束时变量已变成最后一个值。用默认参数在定义时钉死即可。

**Q3：生成器为什么第二次遍历是空的？**
生成器是一次性的迭代器，走完就耗尽。要反复遍历就 `list(gen)` 转成列表，或重新生成一个。

**Q4：装饰器不加 `@functools.wraps` 会怎样？**
返回的 `wrapper` 会丢掉原函数的 `__name__`、`__doc__`，日志、文档、调试都错乱。所以写装饰器默认就加。

**Q5：什么时候该上函数式？**
数据转换管道、排序 key、装饰器、纯计算缓存很合适；复杂状态机、需要清晰调试、团队不熟时，别硬上。

### 本篇知识地图

| 知识点 | 一句话要点 | 关键结论 |
|--------|-----------|---------|
| 函数是一等对象 | 可赋值/传参/返回 | 高阶函数是装饰器的地基 |
| 函数对象属性 | `__name__`/`__doc__`/`__defaults__`/`__code__` | 调试和 wraps 都靠它 |
| lambda | 单表达式匿名函数 | 简单一次性才用，复杂用 def |
| 推导式 | 一行构造容器 | 有独立作用域，不泄漏变量 |
| 生成器表达式 | 惰性求值 | 省内存，但只能遍历一次 |
| 迭代器协议 | `__iter__`/`__next__`/`StopIteration` | for 循环的底层原理 |
| map / filter / reduce | 标准函数式工具 | 简单场景推导式更可读 |
| functools | partial / lru_cache / reduce | 缓存要求参数可哈希 |
| operator | itemgetter / attrgetter | sorted key 的利器 |
| 闭包 | 内层函数记住外层变量 | 存在 cell 对象里 |
| nonlocal | 修改外层变量 | 不加会 UnboundLocalError |
| 装饰器 | 函数作参数、返回新函数 | 记得加 wraps |
| 纯函数与副作用 | 同参同果、不改外部 | 可测试/可缓存/易并行 |
| 选型 | 函数式是工具不是信仰 | 与 OOP、过程式混用 |
