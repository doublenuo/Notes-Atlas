# Python 网络编程到底该怎么写？从 socket 到 TCP/UDP 一次讲清楚

网络编程是 Python 里「最底层也最有掌控感」的一块——直接用 `socket` 和操作系统对话。但底层意味着你要自己处理那些「高级库帮你藏起来的坑」：粘包、字节序、编码、`recv` 的返回值。这篇就从 `socket` 讲起，把这些坑一次讲透。

适合想搞懂「HTTP 请求底层到底发生了什么」，或者要写 TCP/UDP 服务、做网络工具、调试连接问题的人。读完你能想明白三件事：**socket 怎么建立连接、TCP 和 UDP 各有什么坑、以及底层套接字和 `requests` 这类高层库是什么关系**。

## 一、网络基础：IP、端口与 TCP/UDP

### IP 与端口

网络通信要回答两个问题：**发给哪台机器**、**发给机器上的哪个程序**。

- **IP 地址**定位主机（比如 `127.0.0.1` 就是「本机」）。
- **端口**定位主机上的进程，范围 0~65535。一个 `IP:端口` 组合（加上协议）才能唯一定位一个网络服务。

`127.0.0.1`（localhost）是回环地址，发出去的数据立刻回到本机，是本地测试网络程序的标准场地——下面所有例子都用它。

### TCP vs UDP

传输层两个主流协议，性格完全相反：

| 特性 | TCP | UDP |
|------|-----|-----|
| 连接 | 面向连接（三次握手） | 无连接 |
| 可靠性 | 可靠，保证不丢、不乱序 | 不可靠，可能丢包、乱序 |
| 数据形式 | 字节流，无消息边界 | 数据报，一条是一条 |
| 速度 | 慢（要握手、确认） | 快 |
| 典型用途 | HTTP、文件传输、数据库 | 视频、直播、DNS、游戏 |

一句话记：**TCP 像打电话**（先拨号、保证对方听到、顺序不乱），**UDP 像寄明信片**（直接扔、可能丢、顺序不定）。需要可靠就用 TCP，追求低延迟、能容忍丢包就用 UDP。

## 二、socket：网络编程的底层接口

### socket 是什么

**CPython 细节①：`socket` 是对操作系统「文件描述符」的封装**。在操作系统眼里，网络连接就是一个文件描述符（fd），读写 socket 和读写文件用的是同一套 `read`/`write` 系统调用。Python 的 `socket` 对象就是把这个 fd 包装了一层，所以你会看到 `recv`/`send` 和 `read`/`write` 长得那么像。

创建 socket 要指定两个东西：**地址族**（用 IPv4 还是 IPv6）和**类型**（字节流还是数据报）。

```python
import socket

print(socket.AF_INET)        # 2  IPv4 地址族
print(socket.SOCK_STREAM)    # 1  TCP（字节流）
print(socket.SOCK_DGRAM)     # 2  UDP（数据报）
```

**注意点**：`AF_INET + SOCK_STREAM` = TCP，`AF_INET + SOCK_DGRAM` = UDP。这是后面所有代码的两个基本组合。

## 三、TCP 编程：客户端与服务端

### 服务端：bind / listen / accept

TCP 服务端三步走：`bind` 绑定地址端口、`listen` 开始监听、`accept` 接受连接（会阻塞，直到有客户端连进来，返回一个**专门用于这次连接**的新 socket）。

```python
import socket

srv = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
srv.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)   # 允许端口快速复用
srv.bind(("127.0.0.1", 9001))
srv.listen(1)

conn, addr = srv.accept()       # 阻塞，等客户端连进来
data = conn.recv(1024)          # 收数据
conn.sendall(b"echo: " + data)  # 回显
conn.close()
srv.close()
```

### 客户端：connect / send / recv

```python
c = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
c.connect(("127.0.0.1", 9001))   # 连到服务端
c.sendall(b"hello")              # 发数据
print(c.recv(1024))              # b'echo: hello'
c.close()
```

**注意点**：`accept` 返回的 `conn` 和监听用的 `srv` 是**两个不同的 socket**——`srv` 只负责「接客」，`conn` 负责和某个具体客户端「对话」。这个区分是理解 TCP 服务端的关键。

### 粘包与半包

**CPython 细节②：TCP 是字节流，没有消息边界**。你发的是「一串字节」，接收方 `recv` 并不知道「一条消息」在哪结束。于是出现两个现象：

- **粘包**：客户端连发两次 `b"hello"`、`b"world"`，服务端一次 `recv` 可能直接收到 `b"helloworld"`——两条消息粘成了一条。
- **半包**：一次 `recv` 也可能只收到 `b"hel"`，剩下的 `b"loworld"` 要下次 `recv` 才拿到。

**误区一：假设一次 `recv` 就能收到完整消息**。这是 TCP 编程里最经典、最隐蔽的 bug。

```python
# 客户端连发两条
c.sendall(b"hello")
c.sendall(b"world")

# 服务端想当然地以为一次 recv 收到一条完整消息
data = conn.recv(1024)
print(data)   # 可能是 b'helloworld'（粘包），也可能只是 b'hel'（半包）
```

**解决办法**：TCP 本身不保证消息边界，所以要**自己定协议**——最常见的是「长度前缀」：先发 4 字节表示消息长度，再发正文；接收方先读长度、再按长度读够正文。或者用 HTTP 那样的 `\r\n` 分隔符协议。

## 四、UDP 编程与字节序

### UDP：sendto / recvfrom

UDP 无连接，不用 `connect`/`listen`/`accept`，直接 `sendto` 发、`recvfrom` 收，每个数据报自带对方的地址。

```python
srv = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
srv.bind(("127.0.0.1", 9003))

cli = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
cli.sendto(b"ping", ("127.0.0.1", 9003))

data, addr = srv.recvfrom(1024)   # 收到数据 + 来源地址
print(data, addr)                 # b'ping' ('127.0.0.1', 51268)
```

**注意点**：UDP 的 `recvfrom` 一次收到**一个完整的数据报**，不存在粘包问题——这是它和 TCP 的本质区别。但它可能**丢包、乱序**，所以适合「丢一两个包无所谓」的场景。

### 字节序与 struct

跨机器传输二进制数据（比如整数、结构体），要处理**字节序**（大端/小端）——不同 CPU 存整数的字节顺序可能相反。网络传输一般约定用**大端**（网络字节序），用 `struct` 打包/解包：

```python
import struct

print(struct.pack(">I", 0x12345678))   # b'\x124Vx'  大端（>）
print(struct.pack("<I", 0x12345678))   # b'xV4\x12'  小端（<）
print(struct.unpack(">I", b"\x12\x34\x56\x78")[0])   # 305419896
```

**注意点**：`>` 表示大端、`<` 表示小端，`I` 表示 4 字节无符号整数。写二进制协议时，发送方和接收方必须约定好字节序，否则数字会完全错乱。

## 五、常见坑与高层封装

### recv / send 的返回值

**误区二：假设 `send` 一定会把数据全部发出去**。`send` 返回的是「实际发送的字节数」，它**可能少于**你请求的长度（比如发送缓冲区满了）。想保证全部发出，用 `sendall`——它会循环发送直到发完或出错。

```python
c.send(b"x" * 100000)     # 可能只发出去一部分，返回值告诉你发了多少
c.sendall(b"x" * 100000)  # 保证全部发完（或抛异常）
```

**误区三：网络传输中文，不 `encode` 直接 `send` 报错**。`send` 只接受 `bytes`，传 `str` 会直接 `TypeError`。

```python
c = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
try:
    c.send("你好")       # TypeError: a bytes-like object is required, not 'str'
except TypeError as e:
    print(e)

c.send("你好".encode("utf-8"))   # 正确：先编码成 bytes
```

**注意点**：`recv` 返回 `b''` 表示**对端已经关闭连接**——这是判断「对方断开了」的标准信号，别当成「收到了空数据」。

```python
data = conn.recv(1024)
if data == b'':
    print("对端关闭了连接")
```

### 地址与 DNS

`getaddrinfo` 把域名解析成 IP 地址（底层就是 DNS 查询），是 `connect` 背后自动做的事情：

```python
info = socket.getaddrinfo("localhost", 80, socket.AF_INET, socket.SOCK_STREAM)
print(info[0][4])   # ('127.0.0.1', 80)
```

### 高层封装与服务器并发模型（简要）

**别用 socket 造 HTTP**。日常发 HTTP 请求，直接用 `urllib.request`（标准库）或 `requests`（第三方，见 013 篇）——它们把「DNS 解析、建立连接、拼 HTTP 报文、处理编码」全包了。socket 只在你需要「自定义协议、写服务端、或理解底层」时才用。

**服务器并发模型**：上面写的服务端一次只能服务一个客户端（`accept` 和 `recv` 都是阻塞的）。要同时服务多个客户端，有三种做法——多线程/多进程（见 007 篇）、异步 `asyncio`（见 010 篇）。底层还是同一个 socket，只是调度方式不同。


## 小结

回头看这条主线：**IP/端口/TCP/UDP → socket → TCP 服务端/客户端 → UDP 与字节序 → 常见坑与高层封装**。三句话收尾：

1. **TCP 是字节流、没有消息边界**，`recv` 不会帮你按「消息」切分——粘包半包要靠自己定协议（长度前缀）。
2. **`send` 不保证全发，用 `sendall`**；`recv` 返回 `b''` 表示对端关闭；中文要先 `encode`。
3. **写 HTTP 请求别用 socket**，用 `requests`/`urllib`；socket 是理解底层和写自定义协议的工具。

### 几个常见问题

**Q1：TCP 和 UDP 到底怎么选？**
要可靠、不乱序（文件、HTTP）用 TCP；追求低延迟、能容忍丢包（直播、游戏、DNS）用 UDP。

**Q2：为什么我一次 `recv` 收到的是「两条消息粘在一起」？**
因为 TCP 是字节流，没有消息边界。发送方连发两次，接收方一次 `recv` 可能全收到。用「长度前缀」等协议自己切分。

**Q3：`send` 和 `sendall` 有什么区别？**
`send` 可能只发出部分数据（返回实际字节数），`sendall` 保证全部发完。发数据默认用 `sendall`。

**Q4：`recv` 返回空字符串 `b''` 是什么意思？**
表示对端已经关闭连接，不是收到了空数据。这是判断「对方断开」的标准信号。

**Q5：发中文为什么报 `TypeError`？**
`socket` 只收发 `bytes`。发送前 `str.encode("utf-8")`，接收后 `bytes.decode("utf-8")`。
