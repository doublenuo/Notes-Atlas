# Python 并发到底该怎么写？从线程到进程一次讲清楚

Python 的并发是个「特殊存在」，因为它身上绑着一个其它语言没有的东西——**GIL**（全局解释器锁）。很多人学 Python 并发都卡在 GIL 上：为什么开了多线程 CPU 却没变快？为什么还要学多进程？这篇文章就从 GIL 讲起，把线程、进程、异步的定位一次理清。

适合写过 Python、想真正理解「什么时候用线程、什么时候用进程、什么时候用异步」，而不是只会抄模板的人。读完你能想明白三件事：**GIL 到底限制了什么、线程和进程各有什么坑、以及并发选型怎么判断**。

## 一、进程、线程与 GIL：Python 并发的特殊性

### 进程与线程

- **进程**：操作系统分配资源的独立单位，每个进程有**独立的内存空间**，进程之间不共享变量，通信要靠 IPC（管道、队列、网络）。
- **线程**：进程内部的执行流，同一进程的多个线程**共享内存**，所以能直接读同一份变量，但也因此需要处理「竞争」。

一句话区分：**进程隔离内存，线程共享内存**。这决定了它们的取舍——线程轻量、通信方便但容易互相踩；进程笨重、但天然隔离。

### GIL 是什么、为什么存在

**CPython 细节①：GIL 是为了保护引用计数**。CPython 用**引用计数**来管理内存——每个对象身上记着「有多少人引用我」，归零就释放。多线程同时对一个对象做 `引用计数 +1/-1` 时，如果两个线程的 `读-改-写` 交错，计数就会算错，导致内存泄漏或过早释放。最省事的保护办法，就是加一把**全局锁**，让**同一时刻只有一个线程执行 Python 字节码**——这就是 GIL。

```python
import sys
print(sys.getswitchinterval())   # 0.005  GIL 默认每 5ms 释放一次
```

**CPython 细节②：GIL 的调度是「轮流执行」而非「真并行」**。一个线程持有 GIL 最多 5ms（`sys.setswitchinterval` 可调），然后强制让出，换别的线程跑。所以多线程在 CPython 里是**交替执行**，永远只有一个线程在跑 Python 代码——这不是真并行。

### GIL 的影响：CPU 密集 vs IO 密集

**误区一：用多线程加速 CPU 密集任务，反而更慢**。

```python
import threading, time

def cpu_work():
    s = 0
    for i in range(30_000_000):
        s += i * i
    return s

start = time.perf_counter()
cpu_work(); cpu_work()
print(f"单线程顺序: {time.perf_counter() - start:.3f}s")

start = time.perf_counter()
ts = [threading.Thread(target=cpu_work) for _ in range(2)]
for t in ts: t.start()
for t in ts: t.join()
print(f"双线程: {time.perf_counter() - start:.3f}s")
# 单线程顺序: 1.443s
# 双线程: 1.480s   没有变快，反而略慢（GIL 切换有开销）
```

CPU 密集任务是「纯计算」，全程要抢 GIL。两个线程抢同一把锁，轮流跑，还额外付了线程切换的开销——所以**没有加速，甚至更慢**。但 IO 密集任务（网络请求、读文件、数据库查询）在等待 IO 时会把 GIL **主动让出去**，让别的线程跑，于是多线程能显著提速。这是选型的头号依据，后面第五节细讲。

**顺带一提**：Python 3.13 引入了**实验性的无 GIL 构建**（free-threading，PEP 703），编译时显式开启后可以真并行。但生态尚在适配中，当前绝大多数生产环境仍是带 GIL 的 CPython，所以下面的结论先按「有 GIL」来。

## 二、threading：多线程入门与线程安全

### 创建线程、join 与 daemon

```python
import threading, time

def worker(name, delay):
    time.sleep(delay)
    print(f"{name} 完成")

t = threading.Thread(target=worker, args=("任务A", 0.1))
t.start()   # 启动线程，立即返回
t.join()    # 等 t 跑完再往下
print("主线程继续")
```

`join()` 是「等这个线程结束」。**误区三：忘记 `join()`，主线程可能先退出**——主线程（脚本）跑完就结束了，如果子线程还没执行完，它的工作就被腰斩。

```python
def worker():
    time.sleep(0.1)
    print("worker 完成")

t = threading.Thread(target=worker)
t.start()
# 不 join，主线程直接结束，worker 的输出可能根本来不及出现
print("主线程结束")
```

`daemon=True` 把线程设为**守护线程**：主线程一结束，守护线程立即被强制终止，不管它跑没跑完。

```python
def daemon_worker():
    time.sleep(0.5)
    print("这条可能永远打印不出来")

t = threading.Thread(target=daemon_worker, daemon=True)
t.start()
print("主线程结束，守护线程被终止")
```

**注意点**：守护线程适合「后台任务、主程序退出就该跟着死」的场景（心跳、日志刷盘）。凡是「必须完整跑完」的任务，别设 daemon，并记得 `join`。

### 竞争条件与 Lock

线程共享内存，所以两个线程同时读写同一个变量会出问题。先看一个很多人不知道的事实——**在 CPython 里，单条 `x += 1` 碰巧是「安全」的**，因为 GIL 让它的字节码不会被中途打断：

```python
counter = 0
def inc():
    global counter
    for _ in range(100000):
        counter += 1   # 单条字节码序列，GIL 下碰巧没被打断

ts = [threading.Thread(target=inc) for _ in range(4)]
for t in ts: t.start()
for t in ts: t.join()
print(counter)   # 400000  看起来「没问题」
```

但这是**假象**。一旦把「读-改-写」拆开、中间插入一个切换点（IO、`sleep`），竞争条件就暴露了：

```python
counter = 0
def inc_buggy():
    global counter
    for _ in range(1000):
        v = counter        # 读
        time.sleep(0)      # 主动让出 GIL，制造切换窗口
        counter = v + 1    # 写回

ts = [threading.Thread(target=inc_buggy) for _ in range(8)]
for t in ts: t.start()
for t in ts: t.join()
print(counter)   # 期望 8000，实际只有 1000 多！更新大量丢失
```

原因：线程 A 读到 `v=100`，然后让出；线程 B 也读到 `v=100`，也写回 `101`。两次操作只加了一次，更新就丢了。**教训：不能依赖 GIL 的「碰巧原子」，只要涉及共享可变状态的「读-改-写」，就必须加锁。**

```python
counter = 0
lock = threading.Lock()

def inc_safe():
    global counter
    for _ in range(1000):
        with lock:          # 拿到锁才进临界区
            v = counter
            counter = v + 1

ts = [threading.Thread(target=inc_safe) for _ in range(8)]
for t in ts: t.start()
for t in ts: t.join()
print(counter)   # 8000  正确
```

`with lock` 保证同一时刻只有一个线程进入临界区。**死锁与 `RLock`（简要）**：如果一把锁被同一个线程连续 `acquire` 两次（比如递归调用），`Lock` 会把自己锁死（死锁）；`RLock`（可重入锁）允许同一个线程重复加锁，但也要相应释放同样次数。日常写「简单互斥」用 `Lock` 就够。

## 三、multiprocessing：多进程与进程间通信

### Process：绕开 GIL

GIL 锁的是「单个进程内的线程」。多进程每个进程**各有一把 GIL**、各有一个解释器，互不干扰，所以 CPU 密集任务用多进程才能真并行。

```python
import multiprocessing as mp

def worker(name):
    print(f"进程 {name} 启动")

if __name__ == "__main__":
    p = mp.Process(target=worker, args=("A",))
    p.start()
    p.join()
    print("进程结束")
```

```python
def cpu_work(_=None):
    s = 0
    for i in range(30_000_000):
        s += i * i
    return s

# 双进程跑同样的 CPU 密集任务：约 0.859s，对比双线程的 1.480s，真实加速
with mp.Pool(2) as pool:
    pool.map(cpu_work, [None, None])
```

**注意点**：Windows/macOS 默认用 `spawn` 启动子进程（会重新导入脚本），所以**必须**把多进程代码放在 `if __name__ == "__main__":` 保护里，且 `target` 函数要能被 pickle（不能是 lambda、局部函数）。Linux 默认 `fork` 没这个限制，但跨平台代码请统一加保护。

### Pool 与进程间通信 Queue

进程内存隔离，**子进程改的变量父进程看不到**，需要通信就得用 `Queue` 或 `Pipe`：

```python
def producer(q):
    q.put("来自子进程的数据")

if __name__ == "__main__":
    q = mp.Queue()
    p = mp.Process(target=producer, args=(q,))
    p.start()
    print(q.get())   # 来自子进程的数据
    p.join()
```

**注意点**：`Queue` 底层做了序列化（pickle），跨进程传大对象有开销。这就是进程的代价——**隔离换来了安全，也换来了通信成本**。

## 四、concurrent.futures：统一的线程/进程池

`concurrent.futures` 用一套接口同时覆盖线程池和进程池，是最高层的并发 API，日常首选它而不是裸 `threading`/`multiprocessing`。

```python
from concurrent.futures import ThreadPoolExecutor, ProcessPoolExecutor

def square(n):
    return n * n

# 线程池：适合 IO 密集
with ThreadPoolExecutor(max_workers=4) as ex:
    print(list(ex.map(square, range(5))))   # [0, 1, 4, 9, 16]

# 进程池：适合 CPU 密集
with ProcessPoolExecutor(max_workers=2) as ex:
    print(list(ex.map(square, range(5))))   # [0, 1, 4, 9, 16]
```

**注意点**：`map` 保序、按提交顺序返回；`submit` 提交单个任务拿 `Future` 对象，配合 `as_completed` 能「谁先完成先处理谁」。`with` 块结束会自动 `shutdown`，优雅回收。

## 五、选型与异步的定位

### CPU 密集 vs IO 密集

并发选型的第一问永远是：**你的瓶颈是 CPU 还是 IO？**

- **CPU 密集**（大量计算、图像处理、加解密）：GIL 让线程白搭，用**多进程**（或 NumPy 等释放 GIL 的库、无 GIL 构建）。
- **IO 密集**（网络请求、读写文件、数据库查询）：线程在等 IO 时会主动让出 GIL，用**多线程**或**异步**。

### 线程 vs 进程 vs 异步

**异步（asyncio）**是第三种选择——单线程内通过**事件循环**切换任务，适合「大量并发 IO、但单个任务本身很轻」的场景（比如同时请求几百个 URL）。它和线程的本质区别是：**线程是操作系统切换，异步是代码协作切换**，没有线程切换开销，但要求代码全程用 `await` 配合，不能有阻塞调用。（异步有专门的篇幅展开，这里只定位。）

**对比表①：进程 vs 线程**：

| 维度 | 进程 | 线程 |
|------|------|------|
| 内存 | 独立，隔离 | 共享 |
| 通信 | IPC（Queue/Pipe），有序列化开销 | 直接读共享变量，需加锁 |
| 创建开销 | 大 | 小 |
| GIL 限制 | 每个进程一把，不受限 | 受同一把 GIL 限制 |
| 适用 | CPU 密集 | IO 密集 |

**对比表②：并发选型**：

| 场景 | 选择 | 原因 |
|------|------|------|
| CPU 密集 | 多进程 / NumPy | 绕开 GIL，真并行 |
| IO 密集（简单） | 多线程 | 等 IO 时让出 GIL |
| 海量并发 IO | 异步 asyncio | 无线程切换开销 |
| 混合 | 进程 + 线程/异步 | 各取所长 |

**注意点**：不要一上来就上多线程——先确认瓶颈。加了并发但没变快，多半是 GIL（该用进程）或任务本身不重（该用异步）或共享状态锁太多（该重新设计）。

## 小结

回头看这条主线：**进程/线程/GIL → threading 与线程安全 → multiprocessing 与进程通信 → concurrent.futures → 选型**。三句话收尾：

1. **GIL 让 CPU 密集任务的多线程无效**，IO 密集任务才适合多线程——这是 Python 并发第一定律。
2. **共享可变状态必须加锁**，别依赖 GIL 的「碰巧原子」；进程之间要靠 Queue 通信，别指望共享变量。
3. **CPU 密集用进程、IO 密集用线程、海量并发 IO 用异步**，不确定就先定位瓶颈。

### 几个常见问题

**Q1：为什么我开了多线程，CPU 占用率还是只有一核？**
因为 GIL。CPU 密集任务多线程只会轮流跑，不会真并行。换成多进程、或用 NumPy 这类会释放 GIL 的库。

**Q2：`x += 1` 到底线程安全吗？**
在 CPython 里单条 `x += 1` 碰巧是原子的，但「读-改-写」一旦拆开或中间有 IO/切换点，就会丢失更新。别赌这个碰巧，该加锁就加锁。

**Q3：multiprocessing 为什么要写 `if __name__ == "__main__"`？**
Windows/macOS 用 spawn 启动子进程，会重新导入整个脚本；不保护的话子进程会递归创建子进程。且 `target` 函数必须可 pickle。

**Q4：线程、进程、异步到底怎么选？**
CPU 密集用进程，IO 密集用线程，海量并发轻量 IO 用异步。先判断瓶颈再选。

**Q5：多进程是不是一定比多线程好？**
不是。进程创建和通信开销大、内存翻倍，IO 密集场景反而笨重。各有用武之地，看场景。
