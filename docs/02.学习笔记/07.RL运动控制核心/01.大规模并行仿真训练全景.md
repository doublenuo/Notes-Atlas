# 大规模并行仿真训练全景

## 强化学习运动控制整体流程

强化学习运动控制与传统机器人控制的一个重要区别，在于控制策略通常需要通过**大量与环境的交互**来学习。对于人形机器人而言，这些交互不仅涉及关节运动，还涉及浮动基座动力学、足地接触、摩擦、碰撞以及跌倒后的状态恢复。如果只在单个机器人实例上采集数据，训练往往会受到采样效率的限制，大规模并行仿真通过同时运行大量环境，让机器人在不同状态下执行动作，并将产生的数据交给强化学习算法更新策略。

运动控制策略的训练可以压缩成一条数据流：
- **Robot Model**（URDF/MJCF/USD）：定义连杆、关节、质量、碰撞几何，它是仿真的物理真值来源，也是 sim-to-real 差距的第一来源；
- **Simulation**：物理引擎（PhysX、MuJoCo 等）在给定控制输入下推演刚体动力学，产出下一时刻的状态；
- **Environment**：在物理状态之上叠加任务逻辑，观测构造、奖励计算、终止判定、重置策略、域随机化；
- **RL Algorithm**：以 PPO 为主的 on-policy 算法，消费环境产生的 `(obs, action, reward, done)` 序列，更新策略网络与价值网络；
- **Policy**：最终产物是一个从观测到动作的映射，通常是一个 MLP 或包含历史编码的循环网络。

这条链路在单环境、CPU 串行的形态下完全成立，但训练一个可用的运动控制策略需要数亿到数十亿环境步，大规模并行改变的不是链路本身，而是每一步的**执行位置与批量形态**：训练循环仍然是策略推理 → 环境 step → 收集 → 更新，但所有环节的数据都以 GPU Tensor 的形式在显存中流转，不再经过 CPU。

### 训练、评估、部署三阶段

| 阶段 | 输入 | 关键活动 | 输出 |
| --- | --- | --- | --- |
| **训练** | 随机初始化的策略网络 | 在数千并行环境中采样，PPO 更新 | checkpoint权重 |
| **评估** | 固定种子的环境配置与固定的checkpoint | 确定性策略推理，统计成功率、跟踪误差、能耗 | 哪个 checkpoint更适合部署 |
| **部署** | 训练好的策略与真机状态估计 | 导出 TorchScript/ONNX，替换观测源（真机传感器代替仿真观测） | 实时控制回路中的推理节点 |

三个阶段最容易在工程上脱节的地方是**观测空间与动作空间的一致性**。
- 训练时观测中的线速度、角速度、足端接触力往往来自仿真特权信息，部署时必须用状态估计器替代；
- 训练时的 action scale、关节顺序、PD 增益必须与真机完全对齐。

这些对齐工作不属于算法问题，但决定了一个训练成功的 checkpoint 能否直接可用。


### 数据流

在一个并行环境中，观测、动作、奖励和终止条件这四个量以张量的形式存在：
- `Observation`：形状 `(num_envs, obs_dim)`，运动控制中通常包含基座角速度、重力投影、 指令（速度/朝向）、关节位置与速度、上一时刻动作和特权观测（如真实线速度、接触力）在训练中可用，部署时需要蒸馏或估计；
- `Action`：形状` (num_envs, act_dim)`，策略输出通常是目标关节位置偏移或 PD 目标，经 action_scale 和 clip 后送入仿真器；
- `Reward`：形状` (num_envs,)`，运动控制的奖励是多项加权和，速度跟踪、姿态惩罚、关节扭矩惩罚、动作平滑、足端腾空时间等，每一项的权重和裁剪方式直接决定学到的步态风格；
- `Done`：形状` (num_envs,)`，布尔张量，在并行环境中，**单个环境的终止不暂停整体仿真**；终止的环境在下一步被自动重置，对应的 done 掩码在 GAE 计算中截断优势传播。

## 仿真平台与训练框架

### 仿真平台

现代大规模运控仿真彻底告别了传统的 CPU 串行计算，全面转向以 GPU 硬件加速为核心的现代并行物理引擎：
- Isaac Gym / Isaac Sim：由 NVIDIA 深度打造，它的核心设计目标是把**环境步进的吞吐量推到极限**，物理求解与渲染高度集成在显存中，支持数十万个环境并行，吞吐量极高，是四足机器人和高自由度人形机器人全栈运控的工业界主流底座；
- MuJoCo (MJX)：基于 JAX 生态，原生支持端到端自动微分与 XLA 全图编译加速，**极度轻量**，非常适合算法快速原型验证与可微分物理研究，MuJoCo 以接触求解的严谨性和确定性著称，软接触模型在抓取、装配、接触丰富任务上是更可靠的选择。

### 训练框架

训练框架作为上层算法的载体，主要负责环境任务逻辑的封装（如地形生成、奖励函数设计）以及高效强化学习算法（如 PPO）的向量化实现：
- **任务环境封装层**：以 Legged Gym / Isaac Lab 为代表，是建立在底层仿真之上的任务包，专门定义了四足、人形机器人的步态奖励、状态观测空间、动作空间以及复杂的随机地形；
- **并行运控算法库**：RSL-RL专为大规模向量化环境深度定制的高性能 RL 库，代码极简、迭代速度极快，对 PPO 算法进行了极致的显存与计算优化。

二者的关系可以概括为：`Legged Gym` 负责定义机器人在仿真世界中如何完成任务，`RSL-RL` 则根据交互结果学习控制策略。

## 大规模并行仿真原理

### 批量语义

Vectorized Environment（VecEnv）不是一个“开了很多进程的 gym.make”，而是一个**单次 step 调用同时推进 `num_envs` 个独立环境**的接口。输入 action 张量的形状是 `(num_envs, act_dim)`，返回的 obs 是 `(num_envs, obs_dim)`，reward 和 done 是 `(num_envs,)`。环境内部不维护 Python 层的逐环境循环；物理引擎一次性对所有实例执行 broadphase、collision detection 和 solver 迭代。

这种设计的代价是**环境之间的解耦必须由显式的隔离机制保证**。Isaac Gym 用 collision filter 让同一场景中的不同机器人实例互不碰撞；状态张量按环境连续排列，使得内存访问 coalesced，GPU 的并行度被吃满。如果环境之间需要真正的独立物理场景（不同地形、不同物体），则需要在场景构建层面分组，而不是依赖单场景内的掩码。

### GPU 并行计算

每个环境拥有自己的一份状态：基座位姿、关节角度与速度、上一时刻动作、回合计时、指令采样值。这些状态在显存中以**连续张量**的形式存储，第一个维度是环境索引。一次 `env.step()` 的实质是：

1. 将 `(num_envs, act_dim)` 的 action 写入 GPU 控制张量；
2. PhysX 在 GPU 上并行推进所有实例的动力学；
3. 通过 Tensor API 刷新 state tensor（`refresh_dof_state_tensor`、`refresh_rigid_body_state_tensor` 等）；
4. 在 GPU 上计算观测和奖励；
5. 对 `done=True` 的环境，用预采样的初始状态覆盖对应行，**auto-reset 是逐行的原地张量写入**，不重建环境对象。

独立状态维护的关键在于：**重置不是异常路径，而是批量更新的一部分**。一个环境终止后，下一步它已经带着新的初始状态继续产生数据，与其余环境完全同步。这正是并行训练不需要“等待最慢的回合结束”的原因。

### Tensor 化状态更新的隐含约束

全链路 GPU 化的收益建立在“数据永不回 CPU”的前提上。一旦在观测计算或奖励计算中插入 `.cpu().numpy()`，整个流水线退化为 CPU-GPU 混合模式。实测中，将 G1 的观测张量强制转 CPU 再转回 GPU，单步耗时从 8 ms 量级跳到 230 ms 量级，GPU 利用率变为一条平直的横线。更隐蔽的情况是 `use_gpu_pipeline` 未显式设为 `True`：Isaac Gym Preview 4 之前的版本默认是 `False`，系统不会给出警告，而是默默用 CPU 处理中间环节，表现为 GPU-Util 接近 0% 而 Python 进程 CPU 占用飙升。

Tensor 化的另一个约束是**观测维度必须在所有环境间一致**。如果不同地形或不同机器人构型产生不同维度的观测，就无法堆叠成一个连续张量。实践中要么用 padding + mask，要么按任务分组使用不同的 VecEnv，而不是在一个 VecEnv 内混合异构观测。


## 一次训练迭代的完整流程

以 RSL-RL 在 Legged Gym 中的 PPO 闭环为参考，一次 `learn()` 迭代可以压缩为六步：

1. N 个并行机器人各走 T 步
2. 保存 obs/action/reward/done/V/旧 log_prob
3. 反向计算 GAE 和 return
4. 展平为 (T×N) 个 transition
5. mini-batch 多 epoch 更新
6. 清空 buffer

### 推理和环境步进

一次迭代内，策略推理和环境步进是**交替执行 T 次**，而不是先做完所有推理再统一`step`。具体循环为：

```python
for t in range(num_steps_per_env):
    actions = policy.act(obs)         
    obs, rewards, dones, infos = env.step(actions)
    buffer.add(obs, actions, rewards, dones, values, log_probs)
```

`num_steps_per_env` 常见取值为 24、32 或 48，它控制每个环境在一次更新前贡献的时间窗口长度：
- 窗口太短，GAE 的优势估计方差大，策略更新方向噪声重；
- 窗口太长，策略在旧参数下走得太远，PPO 的 clip 约束容易被突破，且单次迭代的墙钟时间拉长。

### Replay buffer

收集阶段结束时，buffer 中保存的是 `T × N` 个 transition，每个 transition 包含：

- `obs`：形状 `(T, N, obs_dim)`
- `actions`：`(T, N, act_dim)`
- `rewards`、`dones`：`(T, N)`
- `values`、`log_probs`：`(T, N)`，对应旧策略

GAE 从最后一步向前递推，利用 `dones` 在终止处截断优势传播。计算完成后，`(T, N)` 被展平为 `B = T × N` 的批量，再划分为 `num_mini_batches` 份，每份重复 `num_epochs`（典型 3–10）做 PPO clip 更新。

on-policy 的硬约束是：**这批数据在更新之后即失效**。PPO 在同一批数据上做多个 epoch 的 mini-batch SGD，本质上是用旧策略的 log_prob 作为重要性采样的锚点；一旦参数更新到与旧策略偏离过远，clip 会截断梯度，继续复用只会浪费算力。因此每次 `learn()` 结束后 buffer 被清空，下一轮用更新后的策略重新采样。这解释了为什么并行规模对 on-policy 训练如此关键：**你无法通过反复消费旧数据来弥补采样量的不足，只能让采样本身变快**。

### 一个数值示例

设 `num_envs = 4096`，`num_steps_per_env = 24`，`num_mini_batches = 4`，`num_epochs = 5`。一次迭代产生 `4096 × 24 = 98,304` 个 transition。mini-batch 大小为 `98,304 / 4 = 24,576`。在 5 个 epoch 中，网络看到 5 次全量数据，但每次的参数更新都受旧策略 log_prob 的 clip 约束。如果 `max_iterations = 1500`，总环境步数约为 `98,304 × 1500 ≈ 1.47 × 10^8`。这正是运动控制训练中“一亿步”量级的来源——它不是单个回合的长度，而是并行批量与迭代次数的乘积。


## 训练资源与性能分析

### 核心参数

| 参数 | 含义 | 增大时的收益 | 增大的代价/风险 |
|---|---|---|---|
| `num_envs` | 并行环境数 | 每轮迭代的样本多样性更高，梯度方差下降；墙钟时间随吞吐量近似线性下降，直到 GPU 饱和 | 显存占用上升；超过 sweet spot 后策略在单轮内看到的时间跨度被稀释，简单任务可能“ horizon 太短学不动” |
| `num_steps_per_env` | 每环境每轮采集步数 | 单轮数据窗口更长，GAE 优势估计更平滑 | 旧策略与新策略的偏离增大，clip 频繁触发；单轮墙钟时间拉长 |
| `num_mini_batches` | 每轮更新划分的 mini-batch 数 | 梯度更新的随机性增加，有助于逃离局部行为 | 太小则梯度噪声过大；`B / num_mini_batches` 不宜低于约 256–512 |
| `num_epochs` | 同一批数据的复用轮数 | 样本效率提升 | 超过 clip 容忍范围后收益递减，甚至破坏策略 |

`num_envs` 和 `num_steps_per_env` 共同决定 `B = num_envs × num_steps_per_env`。在固定 `B` 的约束下，增大 `num_envs` 意味着缩短 `num_steps_per_env`——这是并行规模与时间窗口之间的根本权衡。对于接触丰富的任务（如 Shadow Hand），需要更大的 `num_envs` 来覆盖接触模式的多样性；对于需要较长历史才能判断稳定性的 locomotion 任务，`num_steps_per_env` 不宜压得过低。

### FPS、GPU 利用率与 Simulation Throughput

**FPS（每秒环境步数）** 是并行训练最直接的吞吐量指标，定义为 `num_envs × num_steps_per_env × iterations / wall_clock_time`，或直接由每秒完成的 `env.step()` 中所有环境步的总和度量。它同时包含仿真物理和策略推理的开销，是端到端的系统吞吐量。

**GPU 利用率**需要区分：

- **真正的 CPU 瓶颈**：`use_gpu_pipeline=False` 或观测/奖励计算中触发了主机同步，GPU 在等待 CPU 搬运数据，表现为 GPU-Util 长期接近 0%，而 Python 进程 CPU 占用很高。
- **合理的低利用率**：在小 `num_envs` 或轻量物理场景下，GPU 的 SM 没有被喂饱，但系统瓶颈可能已经转移到策略推理或 PPO 更新上。此时增大 `num_envs` 直到 GPU 利用率进入 80%–95% 区间，通常是性价比最高的调优手段。

**Simulation Throughput** 单独剥离物理仿真的速度（每秒物理步数），与策略推理吞吐量区分开。当 `num_envs` 增大到 GPU 物理求解器饱和后，继续增大环境数只会拉长单次 `env.step()` 的耗时，FPS 不再线性增长。找到这个饱和点是并行规模调优的核心工作。

### 调优的基本次序

从显存可承受的较小 `num_envs` 开始，逐步倍增，同时观察三个信号：FPS 是否仍近似线性增长、GPU 利用率是否进入高位平台、每次迭代的策略更新是否仍然带来评估指标的改善。如果 FPS 停止增长而 GPU 利用率已高，说明物理仿真或推理已经饱和，继续加环境数不会缩短墙钟时间；如果 FPS 增长但评估指标恶化，说明单轮内的有效时间窗口被过度稀释，需要回调 `num_envs` 或增大 `num_steps_per_env`。经验 sweet spot：简单 locomotion 任务约 4096–8192，人形等中等复杂度约 4096，接触密集任务可到 8192–16384。


## 训练实验管理

### Checkpoint

运动控制训练的 checkpoint 不应只包含策略网络的 `state_dict`。一个可复现、可继续训练、可部署的 checkpoint 至少应包含：

- 策略网络与价值网络的参数；
- 优化器状态（继续训练时必需）；
- 当前迭代数和总环境步数；
- 观测归一化统计量（mean/std）——部署时若遗漏这一项，策略行为会完全错误；
- 训练配置的完整快照（或可解析的配置引用）。

保存间隔由 `save_interval` 控制，通常设为每数百到数千次迭代。过于频繁的写盘会干扰训练吞吐量，间隔过大则可能在训练发散时丢失最近的可用策略。一个实用策略是**保留最近 K 个 + 按评估指标保留最佳一个**，而不是只保留最后一个。

### TensorBoard

运动控制训练中最值得盯的曲线不是总 reward，而是分解后的信号：

- **平均回合长度**：在速度跟踪任务中，它直接反映机器人是否学会了“不摔倒”。如果回合长度长期停留在几十步，说明终止条件过严或初始状态过难。
- **各项 reward 分量的均值**：总 reward 上升可能被某一项主导（例如存活奖励），而速度跟踪项并未改善。分解曲线能暴露“在正确的方向上没有进展”的情况。
- **策略熵 / 动作标准差**：过早坍缩意味着探索不足，步态可能陷入局部模式；长期不降则说明 clip 或熵系数设置过松。
- **价值损失与解释方差**：价值函数拟合质量差会通过 GAE 污染优势估计，表现为策略更新方向随机。

TensorBoard 足以支撑单机实验；当需要跨多次运行对比或团队共享时，RSL-RL 支持通过 logger 配置接入 Weights & Biases。

### 随机种子

并行训练的一个容易忽视的事实是：即使 `num_envs` 很大，随机种子的影响仍然显著。环境初始状态的采样、指令分布的采样、网络初始化、mini-batch 的划分顺序，都受种子控制。一次表现良好的训练可能只是“运气好”。可靠的实验管理要求**在固定其他设置的前提下，用多个种子（如 42、43、44）重复完整训练，比较均值和方差，而不是只报告最佳种子的曲线**。

种子复现的边界也需要明确：复用同一个种子可以重复相同的启动配置，但硬件或软件版本的变动仍可能改变结果。因此，与种子同等重要的是记录**启动命令、Git revision、依赖锁定文件、仿真后端和关键超参数**。只保存种子而不保存这些上下文，复现无从谈起。

### 评估与复现的最小闭环

一次训练结束后，评估环节至少应做到：

1. 用**独立的固定种子集**构造评估环境，不与训练采样共享随机流；
2. 在**确定性动作**（取均值而非采样）下统计成功率、速度跟踪误差、能耗、步态对称性等任务指标；
3. 确认 checkpoint 能在一个干净的进程中加载并完成推理回放，不依赖训练脚本的隐式全局状态；
4. 将评估用的 checkpoint、配置快照和评估指标一并归档。

复现则是反向验证：从归档的配置和 checkpoint 出发，能否在相同步数内得到统计上可比的评估结果。做不到这一点，前面的所有曲线都只是不可追溯的观察记录，而不是工程资产。
