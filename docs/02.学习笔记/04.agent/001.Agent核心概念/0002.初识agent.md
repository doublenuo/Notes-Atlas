# Agent入门

## 从ChatBot到Agent

### ChatBot是什么

ChatBot 是一种基于自然语言处理（Natural Language Processing，NLP）的人机交互系统，其核心目标是理解用户输入，并生成符合上下文的自然语言回复。早期 ChatBot 主要依赖规则匹配、模板回复以及检索式问答，例如客服机器人、FAQ 系统等，只能处理预先定义好的问题，缺乏真正的语言理解能力。

随着 Transformer 架构的提出以及大语言模型（Large Language Model，LLM）的快速发展，ChatBot 进入了生成式 AI 时代。以 ChatGPT、Claude、Gemini、DeepSeek 等为代表的新一代 ChatBot，不再依赖固定规则，而是利用海量语料训练出的语言模型，**根据上下文预测最可能的下一段文本**，从而具备了接近人类的语言理解、知识推理、代码生成、内容创作以及多轮对话能力。相比传统聊天机器人，其回答更加自然，泛化能力更强，也能够处理开放领域的问题。

Transformer 架构的诞生以及随后大语言模型的爆发，AI 真正拥有了接近人类的常识理解与逻辑推理能力。然而，这一时期的 ChatBot 本质上仍然属于**被动响应式**系统。它能够根据用户输入生成高质量回答，却不会主动规划任务、持续记忆长期目标，也无法自主调用外部工具完成复杂工作。整个交互过程依旧遵循用户提问到模型回答的模式，每一次输出都围绕当前对话展开，而不是围绕最终任务目标展开。因此，尽管 ChatBot 已经极大提升了人机交互体验，但面对软件开发、科研分析、自动化办公、复杂信息检索等需要多步骤规划、持续执行和环境交互的任务时，用户仍需要充当项目经理，不断拆解任务、编写提示词、检查中间结果并决定下一步操作。这种交互方式的效率瓶颈，也直接推动了下一代 AI Agent 的诞生。

### Agent是什么

AI Agent作为一种全新的架构应运而生，它将大模型作为**核心大脑**，配置了感知环境的**传感器**和改变环境的**执行器**，让 AI 能够像人类一样进行自主规划、记忆留存和工具调用。	

![Agents模式](https://raw.githubusercontent.com/doublenuo/ubuntu-image/main/image/20260622180152633.png)

与传统 ChatBot 最大的区别在于，**Agent 不再执着于回答问题，而是完成任务**。用户只需要描述最终目标，例如"帮我完成一篇文献调研"、"分析整个 GitHub 项目"、"部署一个网站"、"整理今天所有会议并发送邮件"，Agent 会自主将目标拆解为多个子任务，决定执行顺序，在执行过程中不断调用搜索引擎、数据库、代码解释器、终端、浏览器乃至各种 API，根据环境反馈动态调整执行策略，最终完成整个任务流程，而无需用户逐步指挥每一个步骤。

## Agent组成

**AI Agent** 是一个能够感知环境、进行决策并执行行动，以达成特定目标的智能软件实体，它不仅仅是回答问题的聊天机器人，更是能够动手做事的智能执行者，可以大致认为`Agent = Input(感知) + LLM(大脑) + Planning(规划) + Tool use(工具调用) + Memory(记忆)`

![Agent基本架构](https://raw.githubusercontent.com/doublenuo/ubuntu-image/main/image/20260622181822732.png)

### 感知

很显然，没有用户请求，Agent根本不会工作，因此Agent 在行动之前，必须先看到和听到外部信息。现代 Agent 已经不限于纯文本输入，而是具备**多模态感知**能力：

-   **文本输入**：用户的自然语言指令、文档内容、代码；
-   **图像 / 视频**：截图、设计稿、图表，Agent 可以直接看图理解；
-   **环境状态**：在计算机操作类 Agent 中，当前系统状态、网页 DOM 结构、当前开发环境等；
-   **工具感知**：搜索引擎结果、API返回结果、Git仓库信息、数据库查询结果等等

感知层的输入经过整合，形成 **Agent 的当前上下文**，送入大脑进行理解和决策。

### LLM

大语言模型（Large Language Model，LLM）承担着类似大脑的角色，负责理解任务、分析环境、推理决策以及生成执行方案。因此，LLM 层是 Agent 架构中的核心组成部分，连接感知层与执行层。感知层获取到用户输入、环境信息或工具返回结果后，会将这些信息转换为**结构化的上下文**传递给 LLM。大模型首先对当前任务进行语义理解，识别用户意图和任务目标，然后结合已有知识、历史记忆以及当前环境状态进行推理分析，最终生成下一步行动决策。

例如用户向 Agent 提出：帮我查询明天北京到上海的机票，并推荐价格最低的航班。感知层首先提取用户需求，随后 LLM 会分析该任务需要完成哪些步骤：

1.   理解用户需求
2.   查询航班信息
3.   筛选最低价格
4.   整理结果
5.   把结果返回给用户

在这个过程中，LLM 并不会直接查询机票数据，而是根据当前任务制定执行计划，并决定是否调用搜索工具、数据库接口或者第三方服务获取信息。因此，LLM 的核心职责并不是执行任务，而是负责思考和决策。在现代 Agent 系统中，LLM 往往还具备 **Function Calling** 或 **Tool Calling** 能力。当模型判断自身无法直接完成某项任务时，会主动生成工具调用请求。例如查询天气时调用天气 API，搜索资料时调用搜索引擎，分析文件时调用代码执行器。工具执行完成后返回结果，再由 LLM 对结果进行分析和整合，形成最终答案。

>   LLM决定了整个 Agent 的上限。同一套工具和规划框架，接入能力更强的基础模型，任务完成质量往往有质的飞跃。

### Tool Use

大语言模型虽然具备强大的知识理解和推理能力，但其能力本质上受限于**训练数据和上下文窗口**。模型只能根据已有知识进行推理，而无法直接访问实时互联网、查询数据库、执行代码、调用外部系统或者操作真实世界。因此，仅依靠 LLM 本身很难完成复杂的实际任务。为了解决这一问题，现代 Agent 系统引入了 Tool Use（工具使用）机制。所谓 Tool Use，是指 Agent 在完成任务过程中，根据当前需求**自主选择并调用外部工具**，从而获取额外信息或执行具体操作。工具的加入使得 Agent 从一个会思考的语言模型逐渐演变为一个能够感知环境、操作系统并完成真实任务的智能体。在这个过程中，LLM 负责决策，而工具负责执行。两者相互协作，共同完成任务。

在当前主流 Agent 框架中，Tool Use 已成为最核心的能力之一。无论是搜索引擎、代码解释器、数据库接口、浏览器还是企业内部 API，都可以被抽象为 Agent 可调用的工具。Agent 不再依赖模型参数中存储的知识，而是能够动态获取外部信息和执行实际操作，从而突破传统大模型的能力边界。正是因为 Tool Use 的存在，现代 Agent 才能够完成实时问答、联网搜索、代码执行、数据分析、自动办公、机器人控制等复杂任务。可以说，工具使用能力决定了 Agent 能够触达世界的范围，而推理能力则决定了 Agent 如何使用这些工具。

### Planning

如果说 LLM 是 Agent 的大脑，那么 Planning（规划系统）就是大脑中的执行计划制定模块。规划系统负责将用户提出的复杂目标拆解为多个可执行步骤，并确定每一步的执行顺序，从而指导 Agent 有条不紊地完成任务。对于简单问题，大模型往往可以直接给出答案。然而在真实场景中，用户提出的任务通常具有复杂性、多步骤性和长周期性，完成这一任务需要经历多个阶段，此时 Agent 已无法通过一次推理完成全部工作，而是需要先制定任务计划，再逐步执行。因此便产生了 Planning 模块。规划的本质是**将一个复杂目标拆解为多个子任务**（Subtasks），并确定这些任务之间的依赖关系和执行顺序。通过任务拆解，Agent 可以将原本难以完成的问题转化为多个简单问题逐步解决。

在现代 Agent 中，规划通常与推理过程紧密结合。Agent 不仅需要思考当前应该做什么，还需要思考未来几步应该如何执行。因此 Planning 本质上是一种**面向目标的推理过程**（Goal-Oriented Reasoning），目前常见的规划策略如下所示。

|      策略      |        全称        | 核心思路                                         | 适用场景               |
| :------------: | :----------------: | :----------------------------------------------- | :--------------------- |
|   **ReAct**    | Reasoning + Acting | 交替进行"推理"与"行动"，每次行动后根据结果再推理 | 需要工具调用的动态任务 |
| **Reflection** |      自我反思      | 任务完成后，Agent 对自身输出进行批判性审查并修正 | 代码生成、长文写作     |

在现代 Agent 系统中，规划能力决定了 Agent 能否处理复杂、多步骤和长期任务。如果说 Tool Use 决定了 Agent 能够做什么，那么 Planning 则决定了 Agent 应该如何去做。优秀的规划能力能够显著提高任务完成效率、降低工具调用成本，并增强 Agent 在真实环境中的自主决策能力。

### Memory

记忆（Memory）是 Agent 实现持续交互和长期任务执行的重要能力。如果没有记忆系统，大语言模型每次接收到请求时都只能依赖当前输入进行推理，无法保留过去的对话内容、任务状态以及用户偏好。因此，传统 LLM 本质上是一种无状态（Stateless）系统，而 Agent 则需要通过 Memory 机制构建**有状态**（Stateful）能力。从本质上来看，Memory 的作用是帮助 Agent 保存、检索和管理历史信息，使其能够在不同时间、不同任务以及不同交互轮次之间保持上下文连续性。记忆系统让 Agent 不仅能够理解当前发生的事情，还能够结合过去的经验进行决策和推理。

在 Agent 架构中，Memory 通常位于感知层和推理层之间。当用户输入新的任务后，Agent 会首先检索与当前任务相关的历史记忆，然后将这些信息与当前上下文共同提供给 LLM 进行推理分析。根据存储时间和作用范围的不同，记忆系统通常可以分为短期记忆（Short-Term Memory）和长期记忆（Long-Term Memory）。

-   短期记忆主要用于保存**当前任务执行过程中的上下文信息**，例如最近的对话内容、工具调用结果、任务执行状态以及推理过程。它通常存储在上下文窗口（Context Window）中，并随着对话进行不断更新。当上下文长度达到模型限制时，部分内容会被压缩、摘要或者移除。
-   长期记忆则用于保存**跨会话的信息**，例如用户偏好、历史任务记录、知识积累以及长期目标。长期记忆通常存储在数据库或向量数据库中，通过语义检索的方式动态获取相关内容，并在需要时注入到模型上下文中。

从实现角度来看，现代 Agent 的记忆系统已经不再是简单的聊天记录保存，而是逐渐演变为一种知识管理系统。系统会自动对历史信息进行筛选、压缩、归纳和组织，只保留对未来任务有价值的内容。这样既能够降低上下文成本，又能够提升检索效率。当前主流 Agent 框架通常采用 RAG（Retrieval-Augmented Generation）的思想实现长期记忆。历史信息首先经过向量化处理后存储到向量数据库中，当用户提出新任务时，系统根据语义相似度检索最相关的记忆片段，再将其与当前任务一起发送给 LLM。

## Agent基本循环

要理解Agent的基本循环，我们必须先理解它所处的任务环境。在人工智能领域，通常使用**PEAS模型**来精确描述一个任务环境，即分析其：
- **性能度量(Performance)**：用于评估智能体是否成功完成任务以及完成质量的评价标准
- **环境(Environment)**：智能体所处并与之交互的外部世界，包括任务场景、对象及运行条件
- **执行器(Actuators)**：智能体对环境采取行动、执行操作并产生影响的途径或能力
- **传感器(Sensors)**：智能体感知环境、获取外部信息和反馈数据的输入渠道


Agent基本循环是其自主工作的核心机制，描述了Agent从接收输入到输出结果的完整流程。简单来说，它是一个**思考-行动-观察**的迭代过程，Agent通过这个循环不断与环境互动，直到完成任务。

![Agent Loop](https://raw.githubusercontent.com/doublenuo/ubuntu-image/main/image/20260622185455252.png)

> 在许多现代 Agent 系统中，这一循环还会加入 **Reflection** 机制，对本轮执行过程进行自我评估，例如分析工具调用是否成功、获得的信息是否足够可靠、当前规划是否仍然合理以及是否需要重新制定执行策略。如果发现搜索结果质量较低、工具调用失败或者推理出现偏差，Agent 会主动调整下一步行动，而不是沿着错误路径继续执行。同时，Agent 还会在每一轮循环结束后更新 Memory，将已经完成的任务、获取到的重要信息、用户偏好以及中间推理结果保存下来，为后续推理提供长期上下文支持，避免重复搜索或重复思考，提高整体执行效率。

## Agent能做什么

Agent 的价值并不仅仅体现在能够回答问题，而是在于能够**围绕一个目标自主完成整个任务流程**。从本质上来说，只要任务能够被数字化，并且存在相应的工具接口，Agent 都有机会参与甚至自动完成。相比传统的大语言模型只能生成文本，Agent 可以主动获取信息、调用工具、执行操作，并根据执行结果不断调整后续策略，因此应用范围已经从智能问答扩展到办公自动化、软件开发、数据分析、科研辅助以及机器人控制等多个领域。
- **知识获取**：联网搜索、阅读网页、检索论文、分析文档
- **信息处理**：代码生成、文本编辑、数据分析、图像处理
- **任务执行**：办公自动化、软件开发、机器人控制
- **创意生成**：写作、绘画、音乐创作
- **决策分析**：风险分析、投资分析、市场调研
- **机器人领域**：自主导航、物体识别、动作规划、任务执行
- **Multi-Agent**：协作方式类似于现实世界中的团队合作，多个 Agent 之间可以分享任务、协调合作，共同完成复杂任务。


## Agent的局限性

虽然 Agent 在自主规划、工具调用和复杂任务执行方面展现出了远超传统大语言模型的能力，但这并不意味着 Agent 已经能够像人类一样稳定完成所有工作。事实上，Agent 的能力建立在大语言模型、工具生态以及外部环境之上，因此天然存在一定的局限性。

### 幻觉

Agent 的推理能力来源于大语言模型，而大语言模型本身并不真正理解世界，而是**基于概率预测生成内容**。因此，即使 Agent 能够调用大量工具，它在分析工具返回结果、制定执行计划甚至判断任务是否完成时，仍然可能出现推理错误。例如，Agent 可能误解用户意图、错误分析搜索结果、生成不存在的 API 参数，甚至在多个步骤的推理过程中逐渐偏离真实目标。工具能够帮助 Agent 获取真实数据，但并不能完全消除模型本身的幻觉问题。

### 工具依赖性

**Agent 对外部工具具有较强的依赖性**。现代 Agent 的很多能力都建立在工具调用之上，例如搜索引擎、数据库、浏览器、代码执行器以及各种第三方 API。当这些工具发生故障、接口发生变化、网络连接中断或权限不足时，Agent 即使拥有正确的推理能力，也无法完成对应任务。例如，一个负责查询天气的 Agent，如果天气 API 无法访问，它便无法获取最新数据；一个负责自动办公的 Agent，如果浏览器页面结构发生变化，也可能导致整个自动化流程失效。因此，Agent 的能力不仅取决于模型本身，也受到外部工具生态稳定性的影响。

### 上下文窗口

随着任务复杂度不断提升，上下文窗口和 Token 成本也逐渐成为 Agent 面临的重要挑战。Agent 通常需要经历多轮 ReAct 循环，每一次循环都会产生新的推理内容、工具调用结果以及环境反馈，这些信息都会占用上下文窗口。当执行长流程任务时，历史上下文会越来越长，不仅导致推理速度下降，还会显著增加 Token 消耗和推理成本。如果上下文超过模型支持的长度，系统通常需要对历史信息进行摘要或裁剪，而摘要过程中又可能丢失重要细节，从而影响后续决策的准确性。

### 目标偏移

对于需要执行几十甚至上百个步骤的复杂任务，Agent 并不能保证始终围绕最初目标进行推理。随着不断获取新的信息，模型可能逐渐关注一些次要问题，导致执行策略偏离原始任务。例如，在完成整理某公司财务分析报告的过程中，Agent 可能因为搜索到大量行业信息而不断扩展分析范围，最终生成一份内容丰富却偏离用户需求的报告。


## Workflow 和 Agent 的边界

Workflow和Agent都能自动完成一系列任务，这两者的本质区别，并**不在于是否调用了大模型，而在于决策权究竟掌握在谁的手中**。
- **Workflow**：控制流由开发者预先定义。 每一步的执行顺序都是固定的，AI 只是流程中的一个节点，即使内部使用 LLM，也不会改变整体流程。
- **Agent**：控制流由 AI 决定。 AI 根据当前状态自主推理、规划、选择工具，并根据执行结果不断调整策略，形成闭环，直到判断任务完成。

### Workflow

Workflow 的本质是一种**预定义的、由代码和配置文件严格约束的执行路径**。你可以把它想象成汽车制造车间里的物理流水线，每个机械臂都在固定的工位、固定的时间执行固定的焊接或喷漆动作，即使进来的原材料略有偏差，整个流程的节奏和顺序也不会轻易改变。在软件世界里，Workflow 同样遵循这种确定性逻辑，开发者会使用 BPMN 流程图或者大量的条件分支语句（if-else）来提前规定好每一个步骤的走向。即便我们在某个环节里塞进了大语言模型，那个模型通常也只是充当了一个高级的分类器或信息抽取器，它并不拥有改变主路径的权力，整个流程的骨架在设计阶段就已经被牢牢固定。这种设计追求的是极致的可靠性和可预测性，对于金融审计、财务报销、合规审查等场景而言，每一步都可追溯、每一次运行的结果都大致相同，这是Workflow 的核心价值所在。

正因为 Workflow 的控制流在设计阶段就已经确定，它天然适合那些**业务规则明确、执行路径固定、结果要求一致、需要严格审计**的任务。这类任务最大的特点不是复杂，而是确定。开发者能够提前穷举绝大多数执行路径，因此无需赋予 AI 自主决策的能力。例如企业中的财务报销、合同审批、银行风控、保险理赔、订单处理、CRM 客户流转、IT 运维审批等业务流程，本质上都遵循固定的业务规则，每一步应该调用哪个系统、进行哪些校验、满足哪些条件，都可以在开发阶段提前定义。同样，在 AI 应用中，一些流程高度标准化的场景，例如 RAG、文档解析、信息抽取、内容分类、固定模板报告生成、多步骤数据清洗等，也更适合采用 Workflow 架构。

### Agent

Agent 则完全是另一套运行流程，不再是一个被动的执行者，而是一个在循环中不断自主决策的智能实体。Agent 的工作方式通常被业界总结为 **ReAct 模式**，也就是推理与行动的交替迭代。当给一个 Agent 下达诸如帮我分析上个月销售数据并生成一份策略报告这种含糊且复杂的指令时，它并**不会按照预设的固定路径去跑**，而是会先根据自己的理解进行推理，决定第一步该做什么，比如调用 SQL 工具去查询数据库；接着它会观察查询返回的结果，如果发现数据量过大无法一次性处理，它又会重新推理，决定改为分批抽取并用 Python 脚本做聚合运算；随后它继续行动、继续观察，如此循环往复，直到它自己认为任务目标已经达成。在这个过程中，每一步的具体动作都不是程序员预先写死的，而是由大语言模型根据当前所处的上下文动态生成的。正是这种边思考边行动的能力，让 Agent 能够拥抱不确定性，去处理那些我们无法在编码时穷举所有可能性的开放式任务。

Agent 的控制流**不是由开发者预先定义**，而是由大语言模型根据环境动态决定，因此它更适合那些**目标明确但执行路径未知的开放式任务**。这类任务最大的特点不是规则复杂，而是无法在开发阶段穷举所有可能的执行分支。例如软件开发、科研辅助、数据分析、网络信息调研、市场研究、复杂文档处理、自动化办公、机器人控制等场景，用户往往只能描述最终目标，却无法提前规定每一步应该如何完成。Agent 需要根据执行过程中的实时反馈不断调整策略，必要时自主调用搜索引擎、数据库、浏览器、Python、终端等各种工具，甚至重新规划整个任务流程，以适应不断变化的环境。与此同时，Agent 也特别适合那些**需要长期上下文维护、多轮决策以及持续环境交互的任务**。例如，一个代码 Agent 在修复 Bug 时，不仅要阅读代码、定位问题、修改文件，还需要运行测试、分析报错、再次修改代码，直至所有测试通过；一个科研 Agent 在完成文献调研时，则需要不断搜索论文、筛选相关工作、阅读内容、总结观点、发现知识空白，并根据新的发现重新调整搜索方向。这些任务都不存在唯一正确的执行路径，而是需要 Agent 在执行过程中不断思考、行动和修正，这正是 ReAct 范式的价值所在。
