# Python 面向对象到底该怎么用？从 class 到元类一次讲清楚

如果你是从 Java 或 C++ 过来的，Python 的面向对象第一眼会让人很不习惯：没有真正的 `private`、没有 `interface` 关键字、多继承随处可见，甚至连「类」本身都是一个对象。这些「宽松」不是残缺，而是 Python 的刻意设计——它信奉**鸭子类型**和**组合优先于继承**的实用主义，而不是严格的类型体系。理解了这一点，很多看似奇怪的语法就都有了解释。

这篇文章把 Python 面向对象从 `class` 讲到元类。适合写过函数式代码、想系统补齐 OOP，或者从别的语言转过来、总被 Python 的「不严格」搞懵的人。读完你能想明白三件事：**类在 Python 里到底是怎么组织的、那些下划线和魔法方法是干嘛的、以及什么时候该用 OOP、什么时候不该**。

## 一、类与对象：面向对象的地基

### 类、实例与 self

类是「模板」，实例是「按模板造出来的具体对象」。`__init__` 不是构造函数，而是**初始化方法**——它在对象创建之后被调用，负责往对象里塞属性。真正创建对象的是 `__new__`，但你几乎永远不用碰它。

```python
class Dog:
    def __init__(self, name):
        self.name = name

    def bark(self):
        return f"{self.name}: 汪"

d = Dog("旺财")
print(d.name)    # 旺财
print(d.bark())  # 旺财: 汪
```

`self` 是什么？它就是**当前这个实例自己**。`d.bark()` 之所以能写，是因为 Python 在背后把它转换成了 `Dog.bark(d)`——把实例当作第一个参数塞进去。所以 `self` 不是关键字，只是个约定俗成的名字，你写成 `this` 也能跑，但没人这么干。

**CPython 细节①：属性存哪了**。实例属性存在 `instance.__dict__`，类属性存在 `class.__dict__`。访问一个属性时，Python 按「实例 → 类 → 父类」的顺序一路找上去。这解释了下面这个坑。

### 实例属性 vs 类属性

```python
class A:
    x = 1            # 类属性

a = A()
print(a.x, A.x)      # 1 1
a.x = 2              # 给实例赋值，只是覆盖了实例自己的查找
print(a.x, A.x)      # 2 1  类属性没动
```

读的时候，实例能「看到」类属性；但一旦给实例赋值，只是往 `a.__dict__` 里新加了一个 `x`，类属性本身纹丝不动。

**误区一：可变类属性被所有实例共享**。

```python
class B:
    items = []       # 可变类属性

b1 = B()
b2 = B()
b1.items.append(1)
print(b2.items)      # [1]  两个实例共享同一个列表！
```

因为 `items` 这个列表对象存在**类**上，所有实例读到的都是它。想让每个实例各有一个，就得放进 `__init__`：

```python
class B:
    def __init__(self):
        self.items = []   # 每个实例各一个
```

经验法则：**类属性放「所有实例共享的常量」，实例属性放「每个实例各自的状态」**。可变对象（list/dict/set）永远别当类属性默认值用。

### 实例方法 / 类方法 / 静态方法

三种方法，区别在「第一个参数是谁」：

```python
class M:
    kind = "demo"

    def __init__(self, v):
        self.v = v

    def inst(self):        # 实例方法：第一个参数是实例
        return self.v

    @classmethod
    def cls(cls):          # 类方法：第一个参数是类本身
        return cls.kind

    @staticmethod
    def sta(x):            # 静态方法：没有隐式参数，就是个普通函数
        return x * 2

m = M(10)
print(m.inst())      # 10
print(m.cls())       # demo
print(M.sta(3))      # 6
```

**什么时候用哪个**：需要访问实例状态 → 实例方法；需要访问或改写**类状态**、或者想实现「备选构造函数」→ 类方法；既不碰实例也不碰类，只是逻辑上跟这个类相关 → 静态方法。

**对比表①**：

| 特性 | 实例方法 | 类方法 | 静态方法 |
|------|---------|--------|---------|
| 装饰器 | 无 | `@classmethod` | `@staticmethod` |
| 第一个参数 | `self`（实例） | `cls`（类） | 无 |
| 能否访问实例属性 | ✅ | ❌ | ❌ |
| 能否访问类属性 | ✅ | ✅ | ❌（需显式写类名） |
| 典型用途 | 操作实例数据 | 备选构造器、改类状态 | 与类相关的工具函数 |

## 二、属性与封装：property、`__slots__` 与魔法方法

### 下划线约定与 name mangling

Python 没有真正的 `private`，靠的是**约定**：

- `_x`：单下划线，「这是内部实现，别碰」。约定，无强制。
- `__x`：双下划线，会触发 **name mangling**。

**CPython 细节②：name mangling**。类内部出现的 `__x` 会被解释器悄悄改名为 `_ClassName__x`，目的是防止子类不小心覆盖父类的同名属性。

```python
class C:
    def __init__(self):
        self.__secret = 42

c = C()
print(c._C__secret)    # 42  实际被改名成了 _C__secret
# print(c.__secret)    # AttributeError  原名已经不存在了
```

注意这**不是加密也不是访问控制**——外部照样能通过 `_C__secret` 访问到。它只是为了「父子类属性不打架」的防呆设计。所以别把双下划线当成安全机制用，想表达「私有」就用单下划线约定。

### property：把方法变成属性

`property` 让你在「读属性、写属性」时偷偷执行逻辑，对外看起来却还是普通的属性访问。

```python
class Temp:
    def __init__(self):
        self._c = 0

    @property
    def c(self):
        return self._c

    @c.setter
    def c(self, v):
        if v < -273:
            raise ValueError("温度不能低于绝对零度")
        self._c = v

t = Temp()
t.c = 25          # 走 setter，做了校验
print(t.c)        # 25
```

**好处**：可以把「直接访问属性」的旧代码，平滑升级成「带校验/计算的属性」，而不改调用方。这是 Python 相对 Java 的 getter/setter 更优雅的地方——你永远可以从裸属性升级成 property 而不破坏外部接口。

### `__slots__`：给实例减肥

**CPython 细节③：`__slots__` 用描述符省掉 `__dict__`**。默认每个实例都背着一个 `__dict__` 字典存属性，灵活但占内存。`__slots__` 声明了固定的属性名后，CPython 用描述符直接分配固定内存槽，实例就不再需要 `__dict__` 了。

```python
class S:
    __slots__ = ("x", "y")
    def __init__(self, x, y):
        self.x, self.y = x, y

s = S(1, 2)
print(s.x, s.y)               # 1 2
print(hasattr(s, "__dict__"))  # False  没有 __dict__ 了
```

代价也很直接：**不能随便加新属性**了（`s.z = 3` 会报错）。所以 `__slots__` 适合「要创建海量小对象、且属性固定」的场景，比如游戏里的坐标点、金融里的行情快照。普通业务类别用它，省那点内存换来的不灵活不划算。

### 魔法方法：`__str__` / `__repr__` / `__eq__`

以双下划线开头结尾的方法叫魔法方法，Python 会在特定时机自动调用它们。最常用的三个：

```python
class P:
    def __init__(self, x, y):
        self.x, self.y = x, y

    def __repr__(self):
        return f"P({self.x}, {self.y})"   # 给开发者看，尽量能「还原」对象

    def __str__(self):
        return f"点({self.x},{self.y})"    # 给用户看，友好

    def __eq__(self, other):
        return (self.x, self.y) == (other.x, other.y)

p = P(1, 2)
print(repr(p))          # P(1, 2)
print(str(p))           # 点(1,2)
print(p)                # 点(1,2)  print 走 __str__
print(P(1, 2) == P(1, 2))   # True  没定义 __eq__ 时，默认比的是身份 is
```

**误区二：`__repr__` 与 `__str__` 分不清**。一句话区分：`__repr__` 的目标是「无歧义」，最好能 `eval(repr(obj))` 还原出对象；`__str__` 的目标是「可读」。`print()` 和 `str()` 走 `__str__`，解释器里直接敲对象、列表里的元素显示走 `__repr__`。一个偷懒的做法是**只写 `__repr__`**——没定义 `__str__` 时，Python 会回退用 `__repr__` 代替。

**`__eq__` 的副作用**：一旦你定义了 `__eq__`，Python 会把对象的 `__hash__` 置为 `None`，意味着它不能再当 `dict` 的键或进 `set`。

```python
class H:
    def __eq__(self, other):
        return True

h = H()
print(h.__hash__)   # None
```

这是刻意设计：相等对象必须哈希一致，你自己定义的 `__eq__` 让 Python 没法保证这一点，于是干脆把哈希关了。需要同时当键，就得自己再实现 `__hash__`。

## 三、继承与多态：super() 与 MRO

### 继承与多态

子类继承父类的属性和方法，重写（override）同名方法就实现了多态。

```python
class Animal:
    def speak(self):
        return "???"

class Cat(Animal):
    def speak(self):
        return "喵"

class Dog(Animal):
    def speak(self):
        return "汪"

for a in [Cat(), Dog()]:
    print(a.speak())   # 喵 汪
```

这段代码的关键在 `for a in [...]`：调用方**只关心对象「能 speak」**，不关心它具体是猫还是狗。这就是 Python 的多态，也是它「鸭子类型」哲学的直接体现——**只要走起来像鸭子、叫起来像鸭子，那它就是鸭子**。你不必让所有动物都继承同一个基类，只要它们都有 `speak` 方法就能放进这个循环。

### super() 与 MRO

单继承里 `super()` 很简单，就是「调用父类」。但一旦遇到多继承和钻石继承，事情就复杂了。

```python
class A:
    def who(self):
        return "A"

class B(A):
    def who(self):
        return "B"

class C(A):
    def who(self):
        return "C"

class D(B, C):   # 同时继承 B 和 C，B 和 C 又都继承 A（钻石）
    pass

print(D.mro())
# [D, B, C, A, object]
print(D().who())   # B
```

`mro()` 返回的是**方法解析顺序**（Method Resolution Order）——Python 找方法的路径就是按这个列表从左到右。

**CPython 细节④：MRO 由 C3 线性化算法算出**。它不是简单的深度优先或广度优先，而是保证三条规则：**子类排在父类前面**、**父类的声明顺序保持**、**所有类只出现一次**。所以 `D(B, C)` 的查找顺序是 `D → B → C → A → object`，`D().who()` 命中第一个实现者 `B`。

**误区三：钻石继承里 `super()` 的调用顺序出乎意料**。

```python
class A:
    def __init__(self):
        print("A init")

class B(A):
    def __init__(self):
        super().__init__()
        print("B init")

class C(A):
    def __init__(self):
        super().__init__()
        print("C init")

class D(B, C):
    def __init__(self):
        super().__init__()
        print("D init")

D()
# A init
# C init
# B init
# D init
```

很多人以为 `D → B → A`，结果却打印出 `A → C → B → D`。原因还是 MRO：`D` 的 MRO 是 `[D, B, C, A]`，所以 `D.__init__` 里的 `super()` 调到 `B`，`B` 里的 `super()` 调到 **`C`**（不是 `A`！），`C` 里的 `super()` 才调到 `A`。**`super()` 的下一站永远由「当前类的 MRO」决定，而不是写死的父类。**

这也解释了为什么多继承里每个类都用 `super()` 配合 `**kwargs` 的写法（协作式多继承）虽然反直觉，但它是唯一能保证每个 `__init__` 恰好被调用一次的方案。真遇到复杂钻石继承，先 `print(类.mro())` 看看顺序，很多困惑当场消解。

## 四、数据类与抽象：dataclass、ABC、组合 vs 继承

### dataclass：消灭样板代码

写一个「只存数据」的类，过去要手写 `__init__`、`__repr__`、`__eq__` 一大坨。`dataclass` 帮你自动生成。

```python
from dataclasses import dataclass

@dataclass
class Point:
    x: int
    y: int

p1 = Point(1, 2)
print(p1)                   # Point(x=1, y=2)
print(p1 == Point(1, 2))    # True  自动实现了 __eq__
```

**注意点**：`@dataclass(frozen=True)` 能把实例变成不可变（类似 `namedtuple`），不能改属性；需要「纯数据、不可变、能当 dict 键」时用它。下面这张表帮你选。

**对比表②**：

| 特性 | 手写 class | dataclass | namedtuple |
|------|-----------|-----------|-----------|
| 样板代码 | 多 | 少 | 极少 |
| 可变性 | 可变 | 可变（可 frozen） | 不可变 |
| 能否自定义方法 | ✅ | ✅ | ❌（继承不可靠） |
| 能否继承 | ✅ | ✅ | ❌ |
| 内存占用 | 高 | 高 | 低 |
| 典型用途 | 有行为的状态对象 | 数据+少量逻辑 | 轻量只读数据 |

### 抽象基类 ABC

Python 的鸭子类型意味着「有 `speak` 方法就是动物」，但有时你想**强制**子类实现某些方法，这时用 `abc.ABC` + `@abstractmethod`。

```python
from abc import ABC, abstractmethod

class Shape(ABC):
    @abstractmethod
    def area(self):
        ...    # 只声明，不实现

class Square(Shape):
    def __init__(self, s):
        self.s = s
    def area(self):
        return self.s * self.s

sq = Square(3)
print(sq.area())   # 9

# Shape()  # TypeError: 不能实例化抽象类，因为 area 没实现
```

**注意点**：ABC 的用途是「约束」——谁继承 `Shape` 却漏了 `area`，实例化那一刻就报错，把 bug 提前暴露。但它和 Java 的 `interface` 不一样：Python 里你**不必**继承 ABC 也能用鸭子类型工作，ABC 只是「需要强制约束」时的补充手段，日常很少用。

### 组合 vs 继承

老生常谈但值得再说一遍：**优先用组合（has-a），继承（is-a）只在真正「是」的时候用**。继承的问题是耦合太死、层次一深就难改；组合则是把一个对象塞进另一个对象里，用接口（方法调用）协作。

```python
# 组合：引擎是汽车的一部分，而不是汽车的父类
class Engine:
    def start(self):
        return "引擎启动"

class Car:
    def __init__(self):
        self.engine = Engine()   # has-a
    def start(self):
        return self.engine.start()

c = Car()
print(c.start())   # 引擎启动
```

判断标准很简单：**「B 是 A」用继承，「B 有 A」用组合**。拿不准的时候，默认选组合。

## 五、进阶与选型：元类与「什么时候用 OOP」

### 元类：类也是对象

在 Python 里，**类本身也是对象**，而它的「类」就是元类（metaclass）。默认的元类是 `type`——用 `type` 动态创建一个类，等价于用 `class` 写出来：

```python
Point = type("Point", (), {"x": 1, "y": 2})
p = Point()
print(p.x, p.y)     # 1 2
print(type(Point))  # <class 'type'>
```

**注意点**：元类是 Python 最深的黑魔法之一，能拦截「类的创建过程」，用来做校验、注册、注入。Django 的 ORM、`dataclass` 本身都建立在元类之上。但**90% 的开发者一辈子不用自己写元类**——你只需要知道「类也是对象、`type` 能造类」就够理解大半框架的魔法了，真需要时再去啃。

### 什么时候用 OOP，什么时候不用

面向对象不是银弹。下面是选型参考。

**适合 OOP 的场景**：

- **状态 + 行为强绑定**：一个「账户」有余额（状态），也有转账、取款（行为），用类封装最自然。
- **领域建模**：把现实世界的实体（订单、用户、订单项）映射成类。
- **需要继承/多态**：多个对象「像鸭子」，但又有共享基类行为。
- **封装变化**：把「可能变的部分」锁进类内部，对外暴露稳定接口。

**不适合 OOP 的场景**：

- **纯数据转换**：一批数据流经 map/filter 管道，硬套类反而累赘——上一篇文章的函数式更合适。
- **一次性脚本**：跑完就扔的逻辑，写类纯属自找麻烦。
- **为了「像面向对象」而面向对象**：只存数据没有行为的类，用 `dataclass` 或 `namedtuple` 就够了，别硬造 `Manager`、`Handler`、`Service` 层层套壳。

**对比表③**：

| 维度 | 面向对象 | 函数式 | 过程式 |
|------|---------|--------|--------|
| 核心抽象 | 对象与消息 | 纯函数 | 步骤与流程 |
| 状态管理 | 封装在对象内 | 尽量不可变 | 全局/局部变量 |
| 典型场景 | 领域建模、GUI、插件 | 数据转换、缓存 | 脚本、一次性流程 |
| 复用方式 | 继承/组合 | 函数组合 | 抽函数 |
| 测试难度 | 中（要 mock 对象） | 低 | 中 |

归根结底，Python 给你的不是「必须面向对象」，而是一把「需要时再面向对象」的工具。三种风格混着用，才是这门语言的本意——这也和它那套鸭子类型、组合优先的哲学一脉相承。

## 小结

回头看这条主线：**类与对象 → 属性与封装 → 继承与多态 → 数据类与抽象 → 元类与选型**。三句话收尾：

1. **Python 的 OOP 是「宽松」的**：没有真 private，靠下划线约定和 name mangling，鸭子类型取代了严格的接口。
2. **可变类属性、`__repr__` vs `__str__`、钻石继承的 `super()` 顺序**，是三个最高频的坑，理解 `__dict__` 和 MRO 就全想通了。
3. **组合优先于继承，元类知道就行别乱写**，`dataclass` 能省掉大半样板代码。

### 几个常见问题

**Q1：`__init__` 和 `__new__` 有什么区别？**
`__new__` 负责**创建**对象并返回实例，`__init__` 负责**初始化**已创建的对象。绝大多数场景只用 `__init__`；只有单例、不可变类型子类化等极少数情况才碰 `__new__`。

**Q2：类属性赋值为什么不会改到类？**
给实例赋值 `a.x = 2` 是往 `a.__dict__` 里写新键，读的时候实例优先于类，所以看起来「覆盖」了。类属性本身在 `class.__dict__` 里没动。

**Q3：`__slots__` 该不该用？**
只有「海量小对象、属性固定」时才用，省内存换不来灵活性。普通业务类别折腾。

**Q4：钻石继承的 `super()` 顺序为什么反直觉？**
因为 `super()` 的下一站由「当前类的 MRO」决定，不是写死的父类。遇到困惑先 `print(类.mro())` 看查找顺序。

**Q5：什么时候用 OOP？**
状态和行为强绑定、领域建模、需要多态时用；纯数据转换用函数式、一次性脚本用过程式，别为了 OOP 而 OOP。

| 知识点 | 一句话要点 | 关键结论 |

| 类与对象 | class 是模板，实例是对象 | `__init__` 是初始化，`self` 是实例自己 |
| 实例 vs 类属性 | 存在各自的 `__dict__` | 可变对象别当类属性默认值 |
| 三类方法 | 区别在第一个参数 | 访问实例用实例方法，改类状态用类方法 |
| 封装 | 下划线约定 + name mangling | Python 没有真 private |
| property | 方法伪装成属性 | 可无痛升级旧接口 |
| `__slots__` | 描述符省掉 `__dict__` | 海量小对象才用 |
| 魔法方法 | `__str__`/`__repr__`/`__eq__` | 只写 `__repr__` 也能顶 `__str__` |
| 继承与多态 | 重写方法即多态 | 鸭子类型：能 speak 就是动物 |
| super() 与 MRO | C3 线性化 | `super()` 下一站看 MRO，不是写死的父类 |
| dataclass | 自动生成样板方法 | frozen=True 变不可变 |
| ABC | 强制子类实现方法 | 日常少用，需要约束再用 |
| 组合 vs 继承 | has-a vs is-a | 默认选组合 |
| 元类 | 类也是对象 | 知道就行，90% 场景不用写 |
| 选型 | OOP 是工具不是教条 | 与函数式、过程式混用 |
