# Python 异常处理到底该怎么写？从 try 到 with 一次讲清楚

Python 的异常处理有个和其它语言很不一样的底色——它信奉 **EAFP**（Easier to Ask for Forgiveness than Permission，先斩后奏），而不是 C、Java 那套「先检查、后操作」的 LBYL。在 Python 里，写 `if key in dict` 逐层检查反而「不地道」，官方更鼓励你「直接做，出问题再捕获」。这一条态度，决定了后面几乎所有语法的形态。

这篇文章把异常处理从 `try` 讲到 `with`。适合写过 Python、但异常一直「凭感觉写」，或者从别的语言转过来、总觉得 Python 的异常机制「太宽松」的人。读完你能想明白三件事：**异常到底是怎么组织起来的、try/except/raise/with 各自该怎么写、以及什么情况该用异常、什么情况该用判断**。


## 一、异常是什么：常见异常与继承体系

### 异常的本质

异常就是程序运行中「出事了」的信号。当某个操作无法继续（除以零、键不存在、类型不对），Python 就**抛出一个异常对象**，如果没有被捕获，它就会沿着调用栈一路往上冒，最终把 traceback 打印出来然后终止程序。所以「报错」不是坏事，它是一份很精确的现场报告。

```python
print(1 / 0)          # ZeroDivisionError: division by zero
print(int("abc"))     # ValueError: invalid literal for int()
print({}["key"])      # KeyError: 'key'
print([1, 2][5])      # IndexError: list index out of range
```

**常见异常速查**：

| 异常 | 触发场景 |
|------|---------|
| `ValueError` | 值类型对但内容不对（`int("abc")`） |
| `TypeError` | 类型错误（`1 + "1"`） |
| `KeyError` | 字典键不存在 |
| `IndexError` | 列表下标越界 |
| `ZeroDivisionError` | 除以零 |
| `AttributeError` | 属性/方法不存在 |
| `FileNotFoundError` | 文件不存在 |
| `KeyError` / `StopIteration` | 迭代器耗尽 |

### BaseException 与 Exception 的分野

**CPython 细节①：异常分两层**。所有异常的根是 `BaseException`，它下面分出两个阵营：`Exception`（普通异常，你能处理的）和「系统级退出信号」——`KeyboardInterrupt`（Ctrl+C）、`SystemExit`（`sys.exit()`）、`GeneratorExit`。

```python
print(issubclass(ValueError, Exception))           # True
print(issubclass(KeyboardInterrupt, Exception))    # False
print(issubclass(KeyboardInterrupt, BaseException)) # True
```

这条线的意义重大：**`except Exception` 接不住 Ctrl+C**，而裸 `except:` 会连 Ctrl+C 一起吞掉。所以下面这两个习惯的区别，决定了用户按 Ctrl+C 时你的程序是「干净退出」还是「卡死」。

## 二、try/except/else/finally：异常处理的完整语法

### try/except 基础与 as e

```python
try:
    result = 10 / 0
except ZeroDivisionError as e:
    print(f"捕获到: {type(e).__name__}")   # 捕获到: ZeroDivisionError
```

`as e` 把异常对象绑到变量 `e` 上，你可以读它的 `args`、自定义字段，甚至打印它的 traceback。注意 `except` 块结束后 `e` 会被清理，这是 Python 3 为了释放引用做的处理，别在块外访问它。

### 捕获多个异常与 except 顺序

一个 `except` 可以接多个异常类型，用元组写：

```python
try:
    int("abc")
except (ValueError, TypeError) as e:
    print("捕获到:", type(e).__name__)   # 捕获到: ValueError
```

**误区一：except 顺序写错**。`except` 是从上往下**依次匹配**的，一旦命中就不再往下看。所以要把**子类写在前、父类写在后**：

```python
try:
    int("abc")
except Exception:
    print("通用异常")       # 先匹配到这里
except ValueError:
    print("ValueError")    # 永远不会执行！被上面抢先了
```

如果顺序反过来——`ValueError` 在前、`Exception` 在后——才是正确的，具体异常先处理，通用异常兜底。

### else 与 finally

```python
def demo(n):
    try:
        r = 10 / n
    except ZeroDivisionError as e:
        print("except:", type(e).__name__)
    else:
        print("else: 没异常，结果是", r)
    finally:
        print("finally: 总是执行")

demo(2)   # else: 没异常，结果是 5.0 / finally: 总是执行
demo(0)   # except: ZeroDivisionError / finally: 总是执行
```

- **`else`**：只有 try 块**没抛异常**时才执行。它存在的意义是「把「正常逻辑」和「异常处理」分开」，让 try 块只放可能出错的操作。
- **`finally`**：**无论是否异常、是否 return，都会执行**。它专门用来做清理——关文件、释放锁、回滚事务。

**误区二：`finally` 里的 `return` 会覆盖 try 里的返回值**。

```python
def f():
    try:
        return 1
    finally:
        return 2

print(f())   # 2  # 不是 1！finally 的 return 抢了先
```

**CPython 细节②：`finally` 的执行时机**。`finally` 是在 `return` 真正把值交出去**之前**、以及异常往外传播**之前**执行的。所以如果 `finally` 里也写了 `return`，它会覆盖掉 try 里准备好的返回值；如果 `finally` 里抛了异常，也会把 try 里的异常顶掉。经验法则：**`finally` 里只做清理，不写 `return`、不抛异常**。

## 三、抛出与自定义异常：raise、异常链

### raise 与重新抛出

`raise` 主动抛异常：

```python
def divide(a, b):
    if b == 0:
        raise ValueError("除数不能为零")
    return a / b

divide(1, 0)   # ValueError: 除数不能为零
```

**裸 `raise` 重新抛出**：在 `except` 块里写一个光秃秃的 `raise`，会把**当前正在处理的异常原样再抛出去**，而且**保留完整的原始 traceback**。

```python
try:
    try:
        1 / 0
    except ZeroDivisionError:
        print("内层捕获，记录日志后重新抛出")
        raise            # 原样重抛，traceback 不断
except ZeroDivisionError:
    print("外层接住")
```

这一点很关键：**重新抛出一定要用裸 `raise`，不要写成 `raise e`**——后者会重置 traceback，把「异常最初发生在哪」的信息弄丢，排查起来要命。

### 自定义异常类

自定义异常只需继承 `Exception`，可以加自定义字段：

```python
class MyError(Exception):
    def __init__(self, msg, code):
        super().__init__(msg)
        self.code = code

try:
    raise MyError("出错了", 404)
except MyError as e:
    print(e, e.code)   # 出错了 404
```

### 异常链：raise ... from ...

在 `except` 块里再 `raise` 一个别的异常，会把「原来那个异常」和「新异常」串起来，形成**异常链**。显式用 `from` 指定原因：

```python
try:
    try:
        1 / 0
    except ZeroDivisionError as e:
        raise ValueError("换算失败") from e   # 显式指定原因
except ValueError as e:
    print("cause:", type(e.__cause__).__name__)     # ZeroDivisionError
    print("context:", type(e.__context__).__name__)  # ZeroDivisionError
```

**CPython 细节③：`__cause__` 与 `__context__`**。

- `raise X from Y`：显式把 Y 记为 X 的**原因**，存在 `X.__cause__`。
- 不写 `from`，在 except 里直接 `raise X`：Python 自动把原异常记为**上下文**，存在 `X.__context__`，此时 `__cause__` 是 `None`。

```python
def f2():
    try:
        1 / 0
    except ZeroDivisionError:
        raise ValueError("处理中又出错")   # 没写 from

try:
    f2()
except ValueError as e:
    print(e.__cause__)                       # None
    print(type(e.__context__).__name__)      # ZeroDivisionError
```

**注意点**：`from` 的语义是「这个新异常**是因为**那个旧异常才发生的」，让最终报错能把「根因 → 表象」的链条完整展示出来。写库、写框架时特别重要；日常写业务，理解了就行，不必处处 `from`。

## 四、with 与上下文管理器：让清理自动发生

### with 与 `__enter__` / `__exit__`

`with` 语句背后是**上下文管理器协议**：进入时调 `__enter__`，离开时（无论正常还是异常）调 `__exit__`。它把「获取资源 → 使用 → 释放资源」这套模式自动化了。

```python
class CM:
    def __enter__(self):
        print("进入")
        return self
    def __exit__(self, exc_type, exc_val, tb):
        print("退出", exc_type)
        return False

with CM() as c:
    print("主体")
# 进入
# 主体
# 退出 None
```

`__exit__` 的三个参数是「有没有异常、异常对象、traceback」，正常退出时都是 `None`。你天天用的 `with open(...) as f` 就是靠它保证文件一定被关闭——哪怕中间抛异常。

### `__exit__` 的返回值语义

**误区三：`__exit__` 返回 `True` 会静默吞掉异常**。

```python
class Swallow:
    def __enter__(self):
        return self
    def __exit__(self, exc_type, exc_val, tb):
        return True    # 返回 True = 「异常我已处理，别往外传」

try:
    with Swallow():
        1 / 0
    print("没抛出来，异常被吞了")   # 这行会执行
except ZeroDivisionError:
    print("抛出来了")               # 这行不会执行
```

`__exit__` 返回**真值**意味着「吞掉异常」；返回 `False`/`None` 意味着「不处理，让异常继续传播」。绝大多数上下文管理器都该返回 `False`，只有极少数（比如 `contextlib.suppress`）才故意吞异常。**手写 `__exit__` 时，记得末尾 `return False`，别随手 `return True`**。

### contextlib.contextmanager（简要）

用生成器也能写上下文管理器，`yield` 前是 `__enter__`，`yield` 后是 `__exit__`：

```python
from contextlib import contextmanager

@contextmanager
def cm():
    print("进入")
    try:
        yield "value"
    finally:
        print("退出")

with cm() as v:
    print("主体", v)
# 进入
# 主体 value
# 退出
```

**注意点**：`yield` 一定要包在 `try/finally` 里，否则 `with` 块里抛异常时，`yield` 之后的清理代码不会执行。这个装饰器适合「临时、简单」的上下文管理；需要完整控制时再写 `__enter__`/`__exit__` 类。

## 五、异常处理的哲学：EAFP 与选型

### EAFP vs LBYL

- **LBYL**（Look Before You Leap，先问后做）：先检查条件，再执行操作。
- **EAFP**（Easier to Ask Forgiveness，先斩后奏）：直接做，抛了异常再处理。

```python
# LBYL：先检查
d = {"a": 1}
if "b" in d:
    print(d["b"])

# EAFP：直接做，出错再捕获
try:
    print(d["b"])
except KeyError:
    pass
```

Python 官方明确偏向 EAFP。原因在于：LBYL 的「检查」和「使用」之间存在**时间窗口**——多线程下检查完键可能就被删了；而且检查往往要重复读一遍数据，更慢、更啰嗦。EAFP 则把这个窗口交给异常机制天然填平了。

**对比表**：

| 维度 | EAFP | LBYL |
|------|------|------|
| 思路 | 先做，出错再捕获 | 先检查，再做 |
| 代码形态 | try/except | if 判断 |
| 多线程安全 | 相对安全 | 检查和使用之间有时间窗口 |
| 可读性 | 正常路径清晰 | 异常路径清晰 |
| Python 态度 | 官方推荐 | 不反对，但非首选 |

### 什么时候用异常，什么时候用判断

**用异常（EAFP）**：操作「通常能成功」，异常是少数情况——查字典、读文件、网络请求、类型转换。

**用判断（LBYL）**：条件检查很便宜、且你**确定**要处理的是「正常分支」而不是「错误」——比如 `if not lst:` 判断空列表、`if x is None`。

**误区四：`except Exception` 太宽，把真正的 bug 吞掉**。捕获越宽，越容易把不该吞的错误一起吞掉，让 bug 静默埋下。原则是**能捕获多具体就多具体**，只处理你预期到的那几种异常，剩下的让它自然往上抛。

## 小结

回头看这条主线：**异常是对象（有继承体系）→ 用 try/except/else/finally 处理 → 用 raise/from 抛出和串联 → 用 with 自动清理 → 用 EAFP 的态度做选型**。三句话收尾：

1. **`except Exception` 接不住 Ctrl+C**，裸 `except:` 才会——所以兜底用 `except Exception`，别用裸 `except:`。
2. **`finally` 里别写 `return`，`__exit__` 别随手返回 `True`**，重新抛出用裸 `raise`——这三处是「静默吞异常」的重灾区。
3. **Python 信奉 EAFP**，能直接做就别先检查；但 `except` 要具体，别一网打尽。

### 几个常见问题

**Q1：`except Exception` 和裸 `except:` 有什么区别？**
`except Exception` 只接普通异常，`Ctrl+C`（`KeyboardInterrupt`）和 `sys.exit()`（`SystemExit`）会穿透它；裸 `except:` 连这些都吞。所以兜底用 `except Exception`。

**Q2：`finally` 和 `except` 谁先执行？**
`except` 先捕获处理，然后 `finally` 才执行；如果 `finally` 里 `return`，会覆盖之前的返回值。

**Q3：`raise e` 和裸 `raise` 有什么不同？**
裸 `raise` 保留原始 traceback；`raise e` 会重置 traceback，把「异常最初发生在哪」的信息弄丢。重新抛出永远用裸 `raise`。

**Q4：`with` 和 try/finally 是什么关系？**
`with` 本质就是 try/finally 的语法糖，保证 `__exit__` 一定被调用。凡是「获取后必须释放」的资源（文件、锁、连接），都用 `with`。

**Q5：什么时候用异常、什么时候用 if 判断？**
操作「通常能成功、出错是少数」用 EAFP 的 try/except；检查便宜且处理的是正常分支，用 if。原则是 except 要具体，别太宽。
